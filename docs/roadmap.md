## 第 0 周 ✅ 工程脚手架

- **目标**：做出可安装、可运行、可验证的工程骨架
- **可演示**：终端执行 `lite-agent --help` 输出用法
- **验收**：
  - `pip install -e ".[dev]"` 退出码 0
  - `lite-agent --help` 退出码 0，输出含 `usage:` 与 `--help`
  - `git status --porcelain` 输出为空
  - `git ls-files` 不含 `.venv/`、`__pycache__/`、`*.egg-info/`
- **风险**：Windows 控制台 GBK 代码页导致中文乱码 → 已用 `PYTHONUTF8=1` 规避

## 第 1 周 🚧 最小可用 Agent Loop

- **目标**：跑通「模型发起 tool_call → 执行 → 回填 → 再次调用」的完整闭环，只带 `read_file` 一个工具
- **可演示**：`lite-agent "读取 pyproject.toml，告诉我项目名和依赖数量"`
- **验收**：
  - 上述命令退出码 0，输出包含 `lite-coding-agent`
  - `--verbose` 打印的消息流中出现 ≥1 次 tool_call 及其对应结果回填
  - `read_file` 读取不存在的文件时返回错误字符串，进程不崩溃、无未捕获异常
  - 工具调用累计达 20 次时主动退出，退出码非 0 并打印中止原因
  - `pytest -q` 全绿，含 ≥3 个基于假 LLM 客户端的 loop 测试
- **风险**：不同厂商 tool_call 的 JSON 结构不一致 → 在 `llm.py` 统一为内部消息结构，本期只对接一家

## 第 2 周 ⏳ 工具系统与流式输出

- **目标**：6 个工具全部可用，参数校验与危险命令拦截到位
- **可演示**：`lite-agent "把 README 里的 TODO 找出来，统计每个文件各有几处"`
- **验收**：
  - bash / read_file / write_file / edit_file / grep / list_dir 各有 ≥1 个单元测试
  - 参数不符合 JSON Schema 时返回结构化校验错误，而非抛出异常
  - `bash` 对含 `git push`、`rm -rf /` 的命令拒绝执行，且有对应测试用例
  - 流式输出下首个 token 在本地网络 2 秒内出现
  - 写操作限定在工作区内，含 `../` 的越界路径被拒绝
- **风险**：Windows 无 `grep`/`rm` 等命令，bash 工具语义不一致 → 核心工具用 Python 实现，shell 仅作补充并限定支持范围

## 第 3 周 ⏳ 四层上下文压缩

- **目标**：长会话不超窗口，且压缩效果可量化
- **可演示**：构造 60 轮以上的会话，连续触发四层压缩后继续对话
- **验收**：
  - 构造超过窗口 60% 的会话，压缩后 token 数低于阈值
  - Tier 1 截断保留头尾各 N 行，中间以省略标记替代
  - Tier 2 对同一文件的重复读取只保留最后一次结果
  - Tier 4 摘要后消息条数减少 ≥50%
  - 压缩后追问「本任务最初的要求是什么」，回答仍包含原始要求
- **风险**：摘要质量不稳定、关键信息被概括掉 → 正是第 4 周约束保留机制要解决的问题，本期先在测试里固定为可复现用例

## 第 4 周 ⏳ 关键约束保留机制与对比实验

- **目标**：把约束保留从「尽力而为」变成「可校验、可自愈」
- **可演示**：打印压缩前后的 `constraints.json` ID 集合，演示丢失后自动重新注入
- **验收**：
  - 从 `AGENTS.md` 按约定格式解析出 C1–C5 共 5 条约束并写入 `constraints.json`
  - 压缩前后约束 ID 集合完全一致
  - 人为从上下文中删掉一条约束后，校验能检出并重新注入（有自动化测试）
  - 同一任务连续运行 20 次，开启机制组约束违反次数为 0
  - 关闭机制组在同等任务下出现 ≥1 次违反；若未出现，需加长任务或增加约束数后重测
- **风险**：对比实验缺乏可信基线、工作量被低估 → 用自建 20 次 × 30 轮任务集作为主线，Terminal-Bench 作为外部参照

## 第 5 周 ⏳ 项目记忆与会话持久化

- **目标**：项目规则自动注入，会话可中断恢复
- **可演示**：`lite-agent --debug-context` 打印已注入的规则；`kill` 后 `lite-agent --resume` 继续上一轮
- **验收**：
  - `--debug-context` 输出包含 C1–C5 全部 5 条约束
  - 子目录 `AGENTS.md` 与根目录规则冲突时，子目录规则生效
  - 会话中途结束进程，`--resume` 后的消息历史与中断前一致
  - checkpoint 文件可被 `json.load` 解析，且不含任何密钥明文
- **风险**：多层 `AGENTS.md` 的冲突消解规则容易含糊 → 明确为「就近覆盖同 ID 约束，不同 ID 追加」，并写成测试

## 第 6 周 ⏳ 测试、CI 与评测

- **目标**：项目可被外部独立验证
- **可演示**：GitHub Actions 页面双平台全绿 + README 评测表格
- **验收**：
  - `pytest --cov=src/agent` 覆盖率 ≥70%
  - GitHub Actions 在 `ubuntu-latest` 与 `windows-latest` 双平台 `pytest -q` 全绿
  - README「评测」填入 Terminal-Bench 指定 10 个任务的通过数（实际跑出的数字，不是估计）
  - README「参考」一节补上真实可访问的链接
- **风险**：Terminal-Bench 依赖 Linux/Docker，Windows 本地跑不通 → 评测统一放 CI 上执行，本地只跑单元测试

## 当前风险与应对

| 风险 | 影响 | 应对 |
| --- | --- | --- |
| LLM 供应商尚未确定 | `llm.py` 接口结构可能返工 | 先定义内部消息结构，第 1 周只对接一家 |
| 约束提取依赖格式约定 | 用户不按格式写就提取不到 | `AGENTS.md` 中显式声明格式；提取器对不匹配行降级为未编号约束并记录警告 |
| 对比实验缺少可信基线 | 约束保留的收益无法量化 | 自建 20 次 × 30 轮任务集为主，Terminal-Bench 为参照 |
| Windows 与 CI Linux 行为差异 | 本地通过、CI 失败 | 路径与 shell 相关逻辑集中封装，双平台测试 |
| 业余时间投入不确定 | 周计划滑期 | 每周验收独立可交付，滑期只顺延后续周，不阻塞已完成部分 |
| 仓库未发布 | README clone 地址为占位符 | 第 6 周评测数据就绪后一并公开发布 |
