> 版本：v1（2026-10-24）

## 2. 阶段详情

### 阶段 0.0：数据多样性审计（1 天，本地）

- **输入依赖**：`private/sft_data_v4/train.jsonl`、`val.jsonl`、`manifest.json`、`TRAIN_V4_FROZEN.txt`；benchmark 审计与统一数据集方案；6 个行为 held-out task ID；DPO 数据 manifest（只读）。
- **产出物**：
  - `docs/evidence/训练数据多样性审计.md`：结论、缺口、补数据决策。
  - `docs/evidence/训练数据多样性审计.csv`：逐任务一行，字段至少包含 `id, split, category, source, difficulty, constraint_count, constraint_types, context_length_bucket, tools_allowed, check_types, has_full_trajectory, duplicate_group, notes`。
  - `docs/evidence/训练数据审计_manifest.json`：审计脚本版本、输入 SHA、行数、分类计数、未知项计数。
- **验收条件**：
  - 380 train / 80 val 每一行都有分类结果；无法分类的显式写 `unknown` 并计数，不得静默丢弃。
  - 输出 BASE/HARD/CTX/TOOL/CONFLICT 五类计数、每类约束类型覆盖、上下文长度分布、工具集合分布、检查项类型分布、重复项。
  - 输出 HARD 条数、每种约束类型占比，并逐条对照 3.1 的预注册门槛给出“补 / 不补 / 灰区一次性决定”。
  - 审计阶段只读：不改任务定义、不改数据、不跑模型。
- **失败处理**：审计脚本报错则本地修复并重跑；不允许用人工抽样替代全量统计。某行无法解析时写 `unknown` 并保留原始 `id`，不得删除。审计未完成前不得启动 0.1 / 0.2。

### 阶段 0.0a：补数据决策与 SFT 基线重跑（0–1 天）

- **输入依赖**：阶段 0.0 的审计结论；现有数据构造脚本；train-v4 冻结文件；final-test-v2 与 dev 的任务 ID / fixture 清单。
- **产出物**：
  - `docs/evidence/补数据决策.md`：按预注册门槛给出“补 / 不补”，列出缺口类型和数量。
  - 若补数据：`private/sft_data_v5/train.jsonl`、`val.jsonl`、`manifest.json`、`TRAIN_V5_FROZEN.json/.txt`；补数据来源、筛选比例、拒绝原因。
  - 若重跑 SFT：`docs/evidence/训练管线验证.md` 新增“0.0a 补数据后 SFT 基线”一节；adapter 与 run manifest 路径。
- **验收条件**：
  - 决策严格按 3.1 执行；50–79 的灰区必须在看到任何模型结果前做一次性决定并写入文档，之后不调。
  - 若补数据：train 450–500、val 80–100；只补 HARD 或覆盖不足的约束类型；不复制、不换参数凑数；与 final-test-v2、dev 的 task ID / fixture seed 严格不重叠。
  - 新数据全部通过 Qwen tokenizer / tool schema / tool-call 结构门禁；manifest 记录来源、筛选比例、拒绝原因、SHA-256。
  - 若重跑 SFT：沿用 7B + NF4 + r=64 + 3072 + 2 epoch + seed `20261019` + full loss，6 任务 × 10 rollout；报告总体、BASE、HARD、工具结果、stable、`within_steps`。
- **失败处理**：若无法在不重复、不降质的前提下补到 450，停止补数据，保留 380/80 并写“因质量/覆盖不足不补”，不得硬凑。若 SFT 重跑 OOM 或基础设施失败，记录 `error_kind`，只做内存修复，不伪造结果。

### 阶段 0.1：DPO 偏好对预检（0.5 天，依赖 0.0a）

- **输入依赖**：0.0a 的最终 train/val；`private/dpo_v1/` 现有 92 对；6 个行为 held-out task ID；Qwen tokenizer；DPO 配置。
- **产出物**：
  - `docs/evidence/DPO偏好对预检.md`：对数、类别分布、negative_type 分布、prompt token 分布、chosen/rejected 可解析率、泄漏检查。
  - 如重建：`private/dpo_v2/dpo_train.jsonl`、`dpo_val.jsonl`、`manifest.json`。
- **验收条件**：
  - 与 6 个行为 held-out 任务、final-test-v2、dev 严格不重叠；逐条检查 `source_task_id`。
  - chosen / rejected 全部可解析为预期结构；prompt 可被 Qwen chat template 渲染；tool_calls 结构合法。
  - 至少覆盖 TOOL / CONFLICT / BASE 三类；negative_type 至少包含 `appended_prose`、`markdown_fence`、`prefixed_prose` 中的两类。
  - 记录 prompt token 的 min / p50 / max，以及超过 `max_prompt_length` 的条数。
- **失败处理**：发现泄漏则重建并重查；chosen/rejected 不可解析则修构造器；修完仍不能覆盖三类或仍泄漏，写“偏好对不足/存在泄漏，不启动 DPO”，不进入阶段 1 的 DPO 分支。

### 阶段 0.2：GRPO prompt 池组内方差预检（0.5 天，依赖 0.0a）

- **输入依赖**：0.0a 的最终 train/val；`training/reward.py`；与阶段 1 相同的策略模型或服务；6 个 held-out task ID。
- **产出物**：
  - `docs/evidence/GRPO_prompt池方差预检.md`：五类各至少 5 个 prompt、每 prompt 至少 8 次 rollout 的 reward 均值 / 方差 / 通过率。
  - `docs/evidence/GRPO_prompt池方差预检.csv`：逐 prompt 一行。
- **验收条件**：
  - 覆盖 BASE/HARD/CTX/TOOL/CONFLICT 五类；每类至少 5 个 prompt；每 prompt 至少 8 次 rollout。
  - 记录 provider、model_version、system_fingerprint、request_id（缺失时标注，不追溯补）。
  - 明确列出 reward 方差 > 0 的 prompt 数量；若全部为 0，写“无组内方差，GRPO 暂缓”。
- **失败处理**：reward.py 不能确定性运行则先修 0.3；若所有 prompt 方差为 0，停止 GRPO 分支，不租卡；若部分方差非零，保留 prompt 列表供 0.8 / 阶段 1 使用。

### 阶段 0.3：reward.py 回归测试（0.5 天，无依赖）

- **输入依赖**：`training/reward.py`、现有 `tests/test_reward_*.py`、任务检查项定义。
- **产出物**：
  - 新增或补全的 `tests/test_reward_*.py`。
  - `docs/evidence/reward回归测试.md`：每个 reward 分量的输入、期望、实际、是否通过。
- **验收条件**：
  - 覆盖 JSON 可解析、snake_case、无 Markdown fence、字段精确匹配、路径不越界、`tools_allowed`、`required_tools_used`、重复同一工具调用、拿到答案后继续调用、`within_steps` 失败。
  - 所有测试确定性、无网络请求；`pytest -q -k reward` 全绿；`ruff check` / `ruff format --check` 通过。
  - 每个扣分项都有正例和负例，不能只测“返回 0”。
- **失败处理**：某分量无法测试时写清原因并标记“未验证”，该分量不得进入 GRPO reward；不得用 `skip` 静默绕过。

### 阶段 0.4：三路径 template 一致性脚本（0.5 天，无依赖）

- **输入依赖**：Qwen tokenizer、SFT 训练渲染、DPO 训练渲染、推理 / 评测渲染、6 个工具 schema、至少 20 条样本轨迹。
- **产出物**：
  - `training/check_template_consistency.py`。
  - `docs/evidence/模板一致性三路径.md` + JSON 报告：每条样本在三条路径下的 token 数、是否含 `# Tools` / `<tools>`、tool_calls 结构、差异原因。
- **验收条件**：
  - 同一轨迹在 SFT 训练、DPO 训练、推理三条路径上的 token 数差 ≤ 5；3 token 的 generation prompt 差异可解释。
  - 三条路径都必须包含工具 schema 和 tool_calls 结构；任何一条缺失 `tools=` 即失败。
  - 20/20 样本通过；失败样本给出具体路径和 token 差异。
- **失败处理**：差异 > 5 或缺失 tools 时先修渲染器，修完重跑；未通过不得进入阶段 1 的 SFT/DPO 训练。

### 阶段 0.5：训练脚本加 3 个开关（0.5 天，无依赖）

- **输入依赖**：`training/train_sft.py`、`training/train_dpo.py`、`training/train_grpo.py`、现有 CLI 与配置。
- **产出物**：
  - 三个开关的实现与 `--help` 文案：
    1. `--loss-mode {full,assistant_only}`：控制 SFT loss 掩码；
    2. `--template-mode {with_tools,without_tools}`：控制训练渲染是否注入工具 schema；
    3. `--max-seq-length`：显式覆盖配置中的序列长度。
  - 对应单测：默认值、显式值、非法值、帮助文本。
  - `docs/evidence/训练脚本开关.md`：开关语义、默认值、影响范围。
- **验收条件**：
  - 三个开关的默认行为与当前已跑配置完全一致；不改变现有 kernel 的默认结果。
  - `--loss-mode assistant_only` 必须走 `LabelPreservingCollator`，不能被默认 collator 覆盖。
  - `--template-mode without_tools` 只用于诊断，不得成为正式训练默认。
  - `pytest`、`ruff check`、`ruff format --check` 全绿；不修改 `core/loop.py`、`compaction.py`、`constraints.py`。
- **失败处理**：任一开关改变默认行为则回滚；单测失败先修测试或实现，不进入 0.6。

  - 现有配置的默认值与当前已跑实验一致；配置校验有单测；`ruff` 全绿。

### 阶段 0.7：数据 SHA 冻结（1 小时，依赖 0.0a）

- **输入依赖**：0.0a 最终 train/val（train-v4 或 train-v5）。
- **产出物**：
  - `private/sft_data_v5/TRAIN_V5_FROZEN.json` 与 `.txt`（若未补数据，则更新 v4 冻结说明并记录“未变更”）。

### 阶段 0.8：预注册门槛写死（1 小时，依赖 0.0a）

### 阶段 0.9：多 seed 评测脚本连跑（0.5 天，无依赖）

- **输入依赖**：评测 runner、固定 6 个 held-out 任务、至少 3 个 seed（`20261019`、`20261020`、`20261021`）。
- **产出物**：
  - 多 seed 运行脚本（或现有脚本的 `--seeds` 支持）。

### 阶段 1：租卡执行（1 天，依赖 0.1–0.9 全部完成）

- **输入依赖**：0.1 DPO 预检、0.2 GRPO 方差预检、0.3 reward 回归、0.4 模板一致、0.5 开关、0.6 配置、0.7 SHA、0.8 预注册、0.9 多 seed 脚本；全部达到验收条件。
- **产出物**：
  - 24 GB 单卡（L4 / A10G 等，实际型号记录）上的 7B QLoRA SFT / DPO / GRPO 运行（按预检结果决定分支）。
  - adapter、run manifest、held-out rollout JSONL、trace、`docs/evidence/阶段1_训练执行.md`。
  - 每个 run 的 GPU 型号、显存、时长、model_version、system_fingerprint、request_id、optimizer step、数据 SHA。
- **验收条件**：
  - 只跑通过预检的分支：DPO 未通过 0.1 则不跑；GRPO 无组内方差或 reward 未验证则不跑。
  - 3 seed；所有组使用同一 pass^k 口径（见 3.4）；报告均值 ± 方差。
  - SFT 至少包含 baseline 与最终数据配方；DPO 至少比较 SFT vs SFT+DPO；GRPO 只有在 reward 通过 0.3 且 0.2 有非零方差时才跑。
  - 0 条伪造结果；失败写 `error_kind`、阶段、GPU 时长、是否重试。
- **失败处理**：
  - DPO smoke 失败 2 次：停止 DPO，写“24GB 不支持 7B DPO”，不试 1024 序列长度。
  - GRPO smoke 失败 1 次：停止 GRPO，写“reward 未验证，GRPO 暂缓”。
  - SFT OOM：只做内存路径修复（序列长度、precompute、checkpointing），记录改动；仍失败则停止并报告。
  - 任一分支失败不阻塞其他已通过分支的收尾，但不能用失败分支写增益。

### 阶段 2：收尾定稿（1–2 天，依赖阶段 1）

  - `docs/evidence/训练管线验证.md` 最终版（含 SFT/DPO/GRPO 或明确的未跑原因）。
  - `docs/evidence/简历措辞.md`、`docs/evidence/面试问答.md` 定稿。
  - 最终验收报告：数字溯源表、限制、未完成项。
- **验收条件**：
  - 每个数字都能追溯到具体 run manifest / CSV / trace；无 TODO、待填、假占位。
  - 项目定位与结果一致；不把 6 任务、3 seed 的描述性结果写成普遍结论。
  - `pytest -q -m "not slow" -k "not mcp"`、`ruff check .`、`ruff format --check .` 全绿。
  - DPO / GRPO / constrained decoding 未跑或失败时，明确写原因，不留空白。
- **失败处理**：结果与旧叙事冲突时改叙事，不改数据；某项未完成则写“未完成 + 原因 + 影响”，不阻塞其他收尾项。

## 3. 预注册项（写死，后续不可事后调整）

以下门槛在本文档创建时固定。任何修改都必须先出新版本、在运行前记录，并说明为什么旧版本不适用；不得在看到结果后调整。

### 3.1 数据审计判定门槛

- HARD 类 **< 50 条**，或任一约束类型占比 **< 10%** → 补数据。
- HARD 类 **≥ 80 条** 且约束类型覆盖均匀 → 不补数据。
- HARD 在 **50–79 条** 为灰区：必须在审计文档中基于覆盖均匀度和缺口做一次性决定并记录，决定后不调；不得等模型结果出来再决定。
- 补数据只补缺口，目标 450–500 train / 80–100 val；不盲目扩到 2000 条。

### 3.2 GRPO 止损规则

- smoke 失败 **1 次** 即停。
- 停止后写：“reward 未验证，GRPO 暂缓”。
- 不进入阶段 1 的 GRPO 分支；不通过换 reward 权重或换 prompt 反复试错。

### 3.3 DPO 止损规则

- smoke 失败 **2 次** 即停。
- 停止后写：“24GB 不支持 7B DPO”。
- 不尝试 1024 序列长度；不通过继续缩短序列或换模型反复试错。
- 两次失败都必须记录 `error_kind`、阶段、GPU 型号/显存、运行时长、是否重试。

### 3.4 pass^k 口径

- 统一用 **k=10 次 rollout 中 ≥6 次通过记为稳定通过**（`stable`）。
- 所有组（baseline / 系统侧 / SFT / DPO / GRPO）使用同一口径。
- 如改用严格 pass^k（10/10 全过），必须在预注册文档中注明，并对所有组统一；不得只对某一组使用严格口径。

### 3.5 多 seed 最低要求

- 最低 **3 个 seed**；报告均值 ± 方差（或标准差，需注明）。
- 单 seed 结果只作为运行记录，不作为结论依据。
- 某个 seed 基础设施失败可重试 1 次；仍失败则报告 2 个 seed 并标注“未达到最低要求”，不得用 1 个 seed 下结论。

## 4. 红线

1. 数据审计必须在 DPO / GRPO 预检之前，顺序不能反。
2. 不盲目扩到 2000 条，只补缺口；不复制、不换参数凑数。
3. 不伪造任何结果；失败写失败原因、`error_kind`、阶段和实际 rollout 数。
4. 不改 `core/loop.py`、`compaction.py`、`constraints.py`。
5. 测试和 lint 全绿；沙箱内 MCP 测试用 `-k "not mcp"`，并记录 WinError 5 是环境限制，不是代码回归。
