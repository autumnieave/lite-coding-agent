  - `docs/evidence/训练数据多样性审计.csv`：逐任务一行，字段至少包含 `id, split, category, source, difficulty, constraint_count, constraint_types, context_length_bucket, tools_allowed, check_types, has_full_trajectory, duplicate_group, notes`。
  - `docs/evidence/训练数据审计_manifest.json`：审计脚本版本、输入 SHA、行数、分类计数、未知项计数。
- **验收条件**：
  - 380 train / 80 val 每一行都有分类结果；无法分类的显式写 `unknown` 并计数，不得静默丢弃。
  - 输出 BASE/HARD/CTX/TOOL/CONFLICT 五类计数、每类约束类型覆盖、上下文长度分布、工具集合分布、检查项类型分布、重复项。

  - 审计阶段只读：不改任务定义、不改数据、不跑模型。
- **失败处理**：审计脚本报错则本地修复并重跑；不允许用人工抽样替代全量统计。某行无法解析时写 `unknown` 并保留原始 `id`，不得删除。审计未完成前不得启动 0.1 / 0.2。

  - `private/heldout_1_5/tasks.jsonl`、fixtures、specs、manifest、SHA-256。
  - 10–20 个跨模板任务，覆盖策略约束、路径/工具白名单、长上下文、冲突取舍、
    多步步骤上限；每个任务必须有确定性检查项。
  - `docs/evidence/阶段1.5a_任务构造.md`：任务清单、模板、约束、可解性验证、与
    train-v5 / dpo_v2 / 旧 6 个 held-out 的重叠检查。
- **验收条件**：
  - 任务数 10–20；模板不是旧 6 任务的简单改名；跨模板维度有明确分布。
  - 与 train-v5 train、DPO prompt、旧 held-out prompt 零重叠；manifest/SHA 冻结。
  - 教师本地验证：每个任务 3 次 rollout 至少 2 次通过；不通过的任务必须修正或剔除
    并记录原因，不能为了凑数降低约束难度。
  - 不把“教师能做”当成“SFT 有增益”；教师验证只用于可解性。
- **失败处理**：任务有歧义或不可解，修正一次或剔除；修正后仍不可解则写“任务无效”，
  不进入 1.5b。不得通过删检查项让教师通过。

#### 1.5b Pilot 评测（Kaggle T4 或租卡，0.5 天）

- **输入依赖**：1.5a 冻结的 10–20 个任务；baseline 与 train-v5 SFT adapter；7B
  Qwen2.5-Instruct + NF4；同一 harness。
- **产出物**：
  - v2：6 个 pilot 任务（easy/medium/hard 各 2）× 10 rollout × baseline/SFT，共
    120 条 rollout；rollout JSONL、trace、逐任务 pass^10、稳定通过（≥6/10）、工具结果、
    within_steps。
  - `docs/evidence/统计heldout_pilot_v2.md`、`统计heldout_pilot_v2_round1.md`、
    `统计heldout_pilot_v2_round2.md` 与对应 CSV。
- **验收条件（v2 预注册）**：
  - 两组使用同一模型、adapter、任务 SHA、judge 和序列配置，0 个 harness error。
  - Round 1 使用 `temperature=0.0`、`top_p=None`、`seed=20261019`；因每次生成重置同一
    seed，10 次 rollout 是确定性重复，只能判为不可估计。Round 2 作为最后一轮，只改采样：
    `temperature=0.7`、`top_p=0.9`、每 rollout seed=`20261019+rollout_index`，任务和
    adapter 不动。
  - 区分度门槛：6 个任务中至少 3 个 baseline 通过率在 20–80%。达到才进入 1.5c。
  - 不达到：第 1 轮退回调难度；第 2 轮仍不达到，写“任务难度无法形成区分度，统计显著
    验证不成立”，停止 1.5，不进入 1.5c/1.5d/1.5e，不再调难度。
- **失败处理**：基础设施失败可重试 1 次；第 2 轮失败即止损，不进行第三轮，不通过事后
  挑任务或修改门槛凑出 20–80%。不得用旧 6 任务或 final-test-v2 的结果替代 pilot。

#### 1.5c 功效分析与预注册（本地，0.5 天）

- **输入依赖**：1.5b 的逐任务通过率与配对差异；最终任务池；固定模型、adapter、数据、
  harness；统计脚本。
- **产出物**：
  - `scripts/power_analysis_1_5.py`（或等价可复现脚本）。
  - `docs/evidence/阶段1.5c_预注册.md`：样本量、任务清单、主要/次要指标、配对单位、
    检验方案、失败/缺失处理、Holm 家族、seed、停止规则。
  - 冻结后 task manifest + SHA-256。
- **验收条件**：
  - 使用 pilot 的基线通过率、SFT 通过率和 discordant 比例做功效计算或模拟；
    目标 power ≥0.8、双侧 α=0.05。
  - 默认分析单位为任务级稳定通过（10 次 rollout ≥6 次）；配对 McNemar；Bootstrap
    按任务重采样（≥10,000 次）；多重比较用 Holm。若改用 rollout 级单位，必须在预注册
    中写清聚类/配对处理，不能事后换口径。

  - 如果所需任务数超过现有 10–20 个，先回到 1.5a 扩任务并重新冻结；不得带着不足

- **失败处理**：pilot 效应接近 0、方差过大或所需样本量不可行时，写“效能不足/任务池
  不足”，停止 1.5d；不得把 underpowered 写成“无显著差异”。

#### 1.5d 正式评测（Kaggle T4 或租卡，1–2 天）

- **产出物**：

  - 0 条伪造/补写；缺失 rollout 原样记录。
- **失败处理**：基础设施失败每组可重试 1 次；仍失败或缺失 >10% 时写“正式评测未完成”，
  不插补、不换 seed、不删失败任务。连续 2 次失败则停止该阶段。

#### 1.5e 统计报告（本地，0.5 天）

## 3. 预注册项（写死，后续不可事后调整）

以下门槛在本文档创建时固定。任何修改都必须先出新版本、在运行前记录，并说明为什么旧版本不适用；不得在看到结果后调整。

### 3.1 数据审计判定门槛

- HARD 类 **< 50 条**，或任一约束类型占比 **< 10%** → 补数据。
- HARD 类 **≥ 80 条** 且约束类型覆盖均匀 → 不补数据。
- HARD 在 **50–79 条** 为灰区：必须在审计文档中基于覆盖均匀度和缺口做一次性决定并记录，决定后不调；不得等模型结果出来再决定。
- 补数据只补缺口，目标 450–500 train / 80–100 val；不盲目扩到 2000 条。

### 3.2 GRPO 止损规则

- smoke 失败 **1 次** 即停。
- 停止后写：“reward 未验证，GRPO 暂缓”。
- 不进入阶段 1 的 GRPO 分支；不通过换 reward 权重或换 prompt 反复试错。

### 3.3 DPO 止损规则（历史条款，已按实际执行更新）

- 历史 T4 分支：smoke 失败 **2 次** 即停，写“T4 16GB 不支持 3072 + 双 7B DPO”；不得试 1024 序列。
- 24GB 分支：未测试，不得把“未测试”写成“不支持”；如需租 24GB，必须先做显存预算，smoke 失败 1 次即停。
- 实际执行：96GB RTX PRO 6000 上 smoke 与全量均通过，DPO 分支已完成；结论只覆盖 58 对 CTX `code_prefix` 偏好，不外推。
- 任何失败都必须记录 `error_kind`、阶段、GPU 型号/显存、运行时长、是否重试；不得把基础设施失败写成方法无效。

### 3.4 pass^k 口径

- 统一用 **k=10 次 rollout 中 ≥6 次通过记为稳定通过**（`stable`）。
- 所有组（baseline / 系统侧 / SFT / DPO / GRPO）使用同一口径。
- 如改用严格 pass^k（10/10 全过），必须在预注册文档中注明，并对所有组统一；不得只对某一组使用严格口径。

### 3.5 多 seed 最低要求

- 最低 **3 个 seed**；报告均值 ± 方差（或标准差，需注明）。
- 单 seed 结果只作为运行记录，不作为结论依据。
- 某个 seed 基础设施失败可重试 1 次；仍失败则报告 2 个 seed 并标注“未达到最低要求”，不得用 1 个 seed 下结论。

### 3.6 阶段 1.5 统计方法（预注册，1.5c 冻结）

- 显著性水平：双侧 α = 0.05；目标功效 ≥ 0.80。
- 主要分析单位：任务级稳定通过（每个任务 10 次 rollout，≥6 次通过记为 stable）；不以单条 rollout 作为独立样本。
- 配对方式：baseline 与 SFT 在同一任务、同一 seed、同一 harness 下配对；使用配对 McNemar 检验任务级 discordant 对。
- 区间估计：按任务重采样 Bootstrap 95% CI，重采样次数 ≥ 10,000；记录随机种子。
- 多重比较：Holm 校正；校正家族在 1.5c 预注册中列全，不事后增删。
- 样本量：由 1.5b pilot 的通过率与 discordant 比例做功效分析或模拟确定，1.5c 冻结；1.5d 不中途改样本量、任务或指标。
- 若任务数不足以达到目标功效，先回 1.5a 扩任务并重新冻结；不得 underpowered 直接跑正式评测。
- 报告口径：显著 / 不显著但有效能 / 效能不足三态，不得把“效能不足”写成“无差异”。

### 3.7 确认性数据独立性（预注册）

- 1.5b pilot 只用于饱和判断和功效分析，**不得**作为 1.5d 的正式证据重复使用。
- 为调难度而修改过的任务，不得以修改前的结果进入确认性分析；修改后必须重新冻结任务与 SHA。
- 1.5d 使用冻结任务集 + 新 rollout；如更换 seed，必须全组统一并在预注册中写清。
- pilot 与正式评测的 rollout、trace、统计结果分开存放，报告中不得混算。
- 旧 6 个 held-out 任务只作历史基线，不进入 1.5 的确认性样本。

## 4. 红线

1. 数据审计必须在 DPO / GRPO 预检之前，顺序不能反。
2. 不盲目扩到 2000 条，只补缺口；不复制、不换参数凑数。
3. 不伪造任何结果；失败写失败原因、`error_kind`、阶段和实际 rollout 数。
4. 不改 `core/loop.py`、`compaction.py`、`constraints.py`。
5. 测试和 lint 全绿；沙箱内 MCP 测试用 `-k "not mcp"`，并记录 WinError 5 是环境限制，不是代码回归。

## 6. 提交与版本规则

1. **每阶段验收后立即 commit + tag**，不攒到最后；tag 命名 `stage-X.X-<slug>`。
2. commit message 统一为 `stage-X.X: 做了什么 + 验收结论`，不写 `update` / `fix` 这类无信息描述。
3. 大文件不进 Git：`private/`、`*.jsonl`（`docs/evidence/*.jsonl` 证据表除外）、`*.safetensors`、`*.pt`、`*.pth`、`*.bin`、`*.whl`、`traces/`、`kaggle_pull_*/`、`tmp_*/`、`**/wheel/`。数据与 adapter 用 manifest + SHA-256 记录版本。
4. 关键结果文档（审计、对比、DPO/GRPO 结果、失败记录）必须进 Git，保证仓库可看到阶段进展。
5. 提交前必须 `pytest -q -k "not mcp"`、`ruff check .`、`ruff format --check .` 全绿；不提交密钥、token、本机绝对路径。
6. 不 force push，不改写已推送历史；阶段修正用新 commit，不 amend 已发布提交。
