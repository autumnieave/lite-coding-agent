# 统一数据集方案

**版本**：v1.5（final-test-v2 + S0/S1 实测 + train-v1；S2 保持预注册）  
**日期**：2026-10-21  
**状态**：`final-test-v1` 因 `U-FT10/11` prompt/fixture 不一致作废（原文件保留）；`final-test-v2` 已冻结并通过 prompt 引用校验；`train-v1` 已生成；S0/S1 已在 v2 上各跑 110 条，S1 为负收益，四组对比不启动；S2 仍为 0 rollout。  
**边界**：这是新数据集，不复用 `scripts/benchmark.py` 的任务实例；原 benchmark 只作为历史回归基线。

## 1. 目标与原则

这个数据集只服务一个问题：在同一套任务分布上，分别观察“系统侧加固”和“训练侧适配”各自带来什么增益，而不是把两套不同任务的结果拼在一起。

四条原则：

1. **一套任务分布、三套 split**：train / dev / test 使用同一 schema、同一难度轴和同一检查口径，但任务 ID、fixture seed 和实例不重叠。
2. **最终 test 预注册、只跑一次**：最终 test manifest 锁定后不再根据结果改任务、改 prompt 或改检查项；调参只在 dev 上做。当前 7+7 是探索性 pilot，**不是**可直接用于四组最终对比的严格 held-out test，原因见 §3.1。
3. **原 benchmark 不混入**：旧 12 任务只回答“历史回归是否仍通过”，不参与统一数据集的训练或 test 统计。
4. **完整轨迹优先**：每个任务必须能导出 `run_start → llm_turn / tool_call / tool_result → run_end`，训练样本和评测样本都保留工具参数与结果，而不是只留 `reply_head`。

## 2. 五维覆盖

| 缺口 | 统一数据集的覆盖方式 |
| --- | --- |
| 难度 | `weak`：1 次工具、1–2 约束；`medium`：2–3 次工具、2–3 约束、文件状态；`strong`：长上下文、冲突/恢复、3+ 约束 |
| 上下文长度 | `short`：1 个 probe；`medium`：2 个用户轮；`long`：10 个上下文文件 + probe，后续可扩到 4k/8k/16k token 阶梯 |
| 检查项 | 每个任务显式列出 `format`、`semantic`、`file`、`tool` 四类检查；不再用“上下文里有代号”冒充行为遵守 |
| 步数预算 | 每个任务给 `min_tool_calls` 和 `steps_limit`；先由最小必要路径定预算，再观察分布，不把 shell 探路算成模型质量 |
| 训练格式 | manifest 固定 `trajectory_events`；后续 runner 必须写完整 messages、tool_calls、tool_results，train/val/test 按 run 隔离 |

### 3.1 pilot test 口径与污染说明

当前 test 不能宣称是“先预注册、后只跑一次”的最终 test。实际执行顺序是：

1. 先跑初版 6 dev + 6 test 的 baseline；
2. 发现 U-T01 检查器误用了 dev 字段名（`file_path` / `raw_value`），修正检查器后重跑了 U-T01；
3. 再新增 U-D07 / U-T07，重新生成并冻结当前 7+7 manifest，然后跑当前 baseline。

因此当前 test 只应称为 **pilot test**：它适合验证任务 schema、检查器和 baseline 分布，不适合作为四组最终对比的 held-out 证据。若确认进入路线 B，必须在看到任何最终 test 结果前重新冻结一份新的 test manifest，四组都只在这份新 test 上各跑一次；不能复用当前 pilot test 的哈希冒充严格预注册。

- dev 与 test 的 task ID、fixture seed（`91xxx` vs `92xxx`）、文件路径和探针细节均不同；不是把同一实例改一个参数。
- 每个任务都把约束原文、检查项、最小必要步数和完整轨迹事件写入 manifest。
- 后续扩充 train 时只复用 schema 和分布轴，不复用 dev/test 的 fixture seed 或任务实例。

## 5. 四组对比

四组共用同一份**最终** test manifest、采样配置和检查器；最终 test 只在四组对比时各跑一次完整 manifest。当前 pilot test 不进入这张对比表。

| 组 | 系统侧加固 | 训练侧 | 用途 |
| --- | --- | --- | --- |
| A. baseline | 否 | 否 | 原始能力与违反分布 |
| B. +系统侧 | 是（dev 选型；constrained decoding 可作为输出格式方案） | 否 | 系统侧净增益 |
| C. +训练 | 否 | 是（只在 train 上） | 训练侧净增益 |
| D. +系统侧+训练 | 是 | 是 | 组合增益与交互效应 |

系统侧迭代只在 dev；训练只在 train；test 不参与任何选择。若 constrained decoding 只在 JSON 输出上有效，B 组只把它用于有 JSON 约束的任务，并在报告中明确作用范围，不能把格式收益外推成工具行为收益。

### 5.1 增益归因口径

最终 test 上不只看四个总分，还要固定同一批 task × rollout 做配对比较：

| 对比 | 公式 | 回答的问题 |
| --- | --- | --- |
| 系统侧净增益 | B − A | 不训练时，系统侧加固单独解决多少检查项/任务 |
| 训练侧净增益 | C − A | 不加固时，训练单独解决多少检查项/任务 |
| 组合增益 | D − A | 两者同时启用后的总变化 |
| 交互项 | D − B − C + A | 两者是否互补，还是系统侧已吃掉训练能解决的问题 |

报告按三层拆分：格式检查（如 `json_valid`）、工具行为检查（`tools_allowed` / `required_tools_used`）、语义与文件检查（内容、路径、恢复）。若 B 组只把格式违反压到 0，而 C/D 组在工具行为上没有增量，应写“训练不必要”，不能把格式收益归功于训练。若 D 显著优于 B 且 C，才讨论训练侧对系统侧残差的补充。

所有差值只报原始计数和配对方向；样本量不足时写“不足以证明”，不伪造置信区间。test 的最终表只在四组各跑一次完整 manifest 后生成一次。

## 6. 预注册指标

每个 task × rollout 记录以下原始计数，不先做显著性包装：

| 指标 | 定义 |
| --- | --- |
| 约束遵守率 | 通过约束检查的检查项数 / 约束检查项总数 |
| 工具调用成功率 | 必需工具调用中返回成功且参数合法的比例；以 trace 的 `tool_calls` / `tool_results` 为准 |
| 任务完成率 | 该任务全部 semantic + file + tool 检查通过的任务数 / 任务数 |
| stable 违反率 | 同一检查项在 10 次有效 rollout 中命中 ≥6 次的比例；1–5 次记 intermittent，0 次不记 stable；有效 rollout 少于 10 次记 insufficient |
| 轨迹完整率 | 含 `run_start`、`llm_turn`、`tool_call`、`tool_result`、`run_end` 的 trace 数 / 总 run 数 |

执行口径：

- 每个 task 先跑 10 次 rollout；baseline dev 与 baseline test 都只记录实际次数和命中数。
- 固定采样配置，不因 stable 不足改 temperature/top_p/seed；若 stable 仍为 0，先改任务难度或上下文轴，不改采样配置。
- 四组 test 各跑一次完整 test manifest；不根据 test 中途结果重跑或筛样本。
- 报告实际 rollout 数和命中数，不伪造置信区间；样本不足就写“样本不足”。

| 约束遵守率 | 通过的约束检查项数 / 约束检查项总数 |
| 工具调用成功率 | 必需工具调用中返回成功且参数合法的比例；以 trace 为准 |
| 任务完成率 | semantic + file + tool 检查全部通过的任务数 / 任务数 |
| stable 违反率 | 同一检查项 10 次 rollout 命中 `>=6` 的比例；1–5 记 intermittent |
| 轨迹完整率 | 含 run_start / llm_turn / tool_call / tool_result / run_end 的 trace 比例 |

### 9.4 四组运行口径

| 组 | 系统侧加固 | 训练侧 | 运行方式 |
| --- | --- | --- | --- |
| A. baseline | 否 | 否 | 一次完整 manifest |
| B. +系统侧 | 是（dev 选型） | 否 | 一次完整 manifest |
| C. +训练 | 否 | 是（只在 train） | 一次完整 manifest |

每个任务预注册 10 个 rollout；四组各跑一次完整 manifest，不因中途结果重跑、不筛任务、
不更换 seed。主报告给原始计数和配对方向；样本不足写“不足以证明”，不伪造置信区间。
pilot test 不进入这张表。
