# train-v1 任务定义公平性审计

**审计对象**：`training/train_split.py` 生成的 22 个 `train-v1` 任务（11 个模板 × A/B 两个 fixture seed）  
**审计方式**：只读任务定义、`scripts/unified_eval.py` 判分器、`src/agent/tools/*` schema，以及 `private/sft_data/traces/train`、`private/sft_data_qwen3/traces/train` 的原始 trace；本阶段不先改任务。  
**对照口径**：DeepSeek `deepseek-flash` 44 条（40/44），Qwen3 `qwen3-coder-flash` 44 条（32/44）；同一 22 任务 × 2 rollout，`temperature=0.0`、`top_p=None`、`seed=20261019`。  
**结论先行**：没有发现 prompt 分隔符、步骤编号、工具 description 或 fixture 路径层面的 DeepSeek 专属偏好；发现的是两个**任务定义与 harness 语义耦合的歧义**，会让“倾向批量调用工具”或“倾向先创建文件”的模型处于不同位置。两个歧义都只影响 4 个 HARD 任务，不足以解释全部 12 条失败。

## 2. 四个审计维度的结论

### 2.1 prompt 措辞

- 22 个任务全部是中文、祈使句、字段名显式；没有 DeepSeek 训练数据常见的“Step 1/2/3”、特殊分隔符、`###` 标题或 XML 标签。
- A/B 两个变体的 prompt 完全相同，只换 fixture seed；不存在“A 给 DeepSeek、B 给 Qwen”的差异。
- 唯一的结构性问题是 CTX-HARD 的多轮措辞：`每读一个文件只回复「已读」`。在 `scripts/unified_eval.py` 中，每个 `user_turn` 调用一次 `AgentLoop.run`，模型一旦输出非工具文本，该轮就结束；因此“读一个、回一个”在 3 轮用户消息内无法读满 10 个文件。DeepSeek 恰好倾向批量调用，Qwen 更常逐文件回复，这会放大为“上下文召回”之外的差异。

### 2.2 工具 schema description

- `read_file` 示例是 `src/agent/core/loop.py`；`write_file` 明确写“父目录不存在会自动创建”；`edit_file` 要求 `old_string` 完全一致且只出现一次；`grep` 示例是 Python 正则；`list_dir` 默认工作区根目录。
- 这些描述是仓库/语言中性的，没有点名某个模型、某个 SDK 或某种输出风格。
- `write_file` 已明确父目录会自动创建，因此 CONFLICT-STRONG 中 Qwen 用 `bash mkdir` 不是 schema 缺失信息，而是工具选择/阅读失败；不需要改 schema。

### 2.3 fixture 路径 / 文件名

- 路径统一为 `project/tuning/...`、`project/notes/...`，A/B 只换 seed，不存在对某个模型更自然的命名。
- TOOL-HARD 的 `files_old` decoy 在 prompt 中被明确点名“不要读取”，不是隐藏陷阱。
- CONFLICT-STRONG 的 `out/` 初始不存在，确实会让模型先尝试建目录；但 `write_file`  description 已说明会自动创建父目录，且 DeepSeek 4/4 不建目录也能正确声明冲突。这个 fixture 细节不是 DeepSeek 专属偏好，但值得在 train-v2 的 prompt 中把“冲突时不要创建/写入”说死。

### 2.4 判分器宽容度

- `parse_json` 是 `json.loads(text.strip())`，不接受 Markdown fence；`no_fence` 单独检查 ```；`answer_exact` 是 `reply.strip() == token`；`read_paths_exact` 是集合恰好相等；`no_arbitrary_file` 是目标路径不存在。
- 这些规则对两个教师完全一致，没有“DeepSeek 风格更宽容”的分支。
- 反证：DeepSeek 的 4 条失败里有 3 条是 fenced JSON / JSON 后追加自然语言（A-TOOL-HARD r0、B-TOOL-HARD r0/r1），说明判分器并没有偏袒 DeepSeek；Qwen 的 JSON 任务反而全部通过。
- 残余风险：`conflict_declared` 关键词表是“冲突/互斥/无法同时/不可能同时/不能同时满足/unresolved/矛盾”，没有“无法全部满足”“不可同时满足”“不能同时成立”。本次 12 条里没有因此误判（失败回复同时含“无法同时满足”），但这是判分覆盖缺口；为避免追溯修改已冻结的 final-test-v2 判分口径，本轮不改，只在文档标注。

## 3. 12 条 coder-flash 失败的归类

逐条明细见 `docs/evidence/coder_flash_12失败归类.csv`。汇总：

| 主分类 | 条数 | 任务 | 说明 |
| --- | ---: | --- | --- |
| 任务歧义（叠加能力） | 3 | A-CTX-HARD r0/r1、B-CTX-HARD r0 | “每读一个文件只回复已读”与 3 轮用户消息冲突；模型只读 2/10 或 6/10 |
| 格式 | 1 | B-CTX-HARD r1 | 读满 10/10、内容正确，但输出 `CODE=CTX-96014`；prompt 已两次要求“严格只输出该值” |
| 能力：算术 | 4 | A/B-TOOL-HARD 各 2 | 读对 7 行 + 9 行，却输出 14 |
| 行为/能力：冲突 | 4 | A/B-CONFLICT-STRONG 各 2 | 声明冲突但仍写 ALPHA；使用 bash；超出 steps_limit |

如果把“行为/能力”并入“能力”，则 **能力 8 / 任务歧义 3 / 格式 1**。格式问题只有 1/12（8.3%），且是 bare-token 前缀，不是 JSON 解析失败；给 coder-flash 加 JSON mode 或 guided decoding 不能解决其余 11 条，因此**不启动 44 条 JSON mode 重跑**。

## 4. 与 DeepSeek 4 条失败的对照

| 教师 | 通过 | 失败任务 | 失败模式 |
| --- | ---: | --- | --- |
| DeepSeek `deepseek-flash` | 40/44 | A-TOOL-HARD r0；B-CTX-HARD r0；B-TOOL-HARD r0/r1 | 3 条 fence/额外文字（值 16 正确）；1 条 CTX 少读 + `CODE=` 前缀 |
| Qwen3 `qwen3-coder-flash` | 32/44 | A/B-CTX-HARD；A/B-TOOL-HARD；A/B-CONFLICT-STRONG | 3 条 CTX 少读；4 条算术 14；4 条冲突写 ALPHA |

这说明：
- 两教师都在同一批 HARD 任务上失败，不是“DeepSeek 拿到简单任务”。
- DeepSeek 的失败偏输出格式，Qwen 的失败偏算术/冲突行为；这是能力/行为差异，不是任务给 DeepSeek 开小灶。
- 但 CTX-HARD 的批量读取歧义确实让“逐文件回复”的模型更吃亏；CONFLICT-STRONG 的“创建”措辞确实让“先创建再解释”的模型多一个被 `no_arbitrary_file` 打掉的机会。这两个歧义需要修正，修正后必须两个教师都在同一套新任务上重跑。

## 5. 本轮决策

1. **只改 train-v2，不动 train-v1、dev、final-test-v2**：
   - CTX-HARD（A/B）：把“每读一个文件只回复已读”改为“本轮内一次性读取该组全部文件（可并行调用 read_file），全部读完后只回复已读”。
   - CONFLICT-STRONG（A/B）：把“若约束无法同时满足，请明确指出，不要自行选择其中一个”改为“若约束无法同时满足，请不要创建或写入 target.txt，只明确指出冲突，不要自行选择其中一个”。
   - 不改文件数、不改 seed、不改约束、不改检查项、不降难度。
2. **两个教师都在 train-v2 上重跑 44 条**（22 任务 × 2 rollout），不出现“DeepSeek 跑旧任务、Qwen 跑新任务”。
3. **不启动 coder-flash 的 JSON mode / guided decoding 44 条重跑**：格式失败仅 1/12，且不是 JSON 解析失败；JSON mode 无法修复其余能力/歧义问题。若未来只针对 `answer_exact` 的 `CODE=` 前缀做 regex constrained decoding，应作为独立系统侧实验，不混入本轮教师对比。
4. **教师决策等 train-v2 双教师结果出来后再下**；在结果出来前不切换教师、不混训、不改 SFT 数据。

## 6. 残余风险与未改动项

- `train-v1` 的 22 个任务实际只有 **11 个唯一 prompt 模板 × 2 个 seed**；有效任务多样性低于“22 个独立任务”的字面含义。这影响统计功效，不影响本轮“12 条失败归因”的逐条证据。
- `CHECK-BASE/HARD` 的 prompt 完全相同，HARD 只是增加检查项；`C1-BASE/HARD` 的 prompt 也相同，HARD 只是增加约束。它们不是内容难度阶梯，文档中应标为“判分/约束强度”而非“任务内容难度”。
- `conflict_declared` 关键词覆盖缺口（见 2.4）本轮不改，避免追溯修改已冻结的 final-test-v2 判分口径。
- 本审计没有发现需要修改 `core/loop.py`、`core/compaction.py`、`core/constraints.py` 的理由；trace 已能提供 `messages`、约束位置、工具调用/结果和最终回复。

### 7.5 教师决策：保持 DeepSeek

**建议保持 `deepseek-flash` 作为 SFT 教师，不切换 `qwen3-coder-flash`。** 理由：

1. v2 同任务同配置下 40/44 vs 31/44，差距 9 条；且 Qwen 的失败在 A/B 两个 fixture 上稳定复现。
2. Qwen 的失败集中在算术（5 条）和冲突行为（4 条），不是格式转换或任务定义偏好；这些错误轨迹作为 SFT 目标会直接教坏模型。
3. Qwen 的 4 条 `CODE=` 前缀失败与 DeepSeek 的 3 条同类失败是同一个输出契约问题，不构成“DeepSeek 被偏爱”的证据。
4. `qwen3-coder-flash` 的探针 6/6 只覆盖 3 个 BASE 任务，不能外推到 HARD；本轮 22 任务 × 2 rollout 是更可信的口径。

数据策略：保留 `private/sft_data`（train-v1，16/5）作为历史；`private/sft_data_v2_deepseek`（train-v2，15/6）可作为下一轮 SFT 的候选，但**不混入 Qwen 数据**。若下一轮使用 v2 数据，先处理 7.6 的 CTX 输出歧义。

### 7.6 残余歧义：CTX-HARD 的 `CODE=` 前缀

fixture 文件中写作 `CODE=CTX-96003`，`final_token` 是 `CTX-96003`；prompt 说“输出 CODE 值”“严格只输出该值”。两教师 v2 都出现输出 `CODE=CTX-96003` 的情况（DeepSeek 3/4，Qwen 4/4），说明“CODE 值”是否包含 `CODE=` 仍有歧义。这不是 DeepSeek 专属偏好，而是共享的输出契约歧义。建议在 train-v3（或 SFT 数据过滤）中明确：“文件中写作 `CODE=ABC` 时，只输出 `ABC`”。本轮不做第三次重跑，因为它不会改变“保持 DeepSeek”的教师决策；但在把 CTX-HARD 用作训练目标前应修正或过滤。

TOOL-BASE/HARD 的“行数”也有 trailing newline 约定问题：Qwen 一次把 7 行文件数成 8 行。该检查是确定性的，且 DeepSeek 在 TOOL-BASE 4/4 通过；本轮把它归类为能力/边界案例，不把“按 splitlines 计数”写进 prompt，以免把任务变成读数练习。
