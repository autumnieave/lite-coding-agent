# 面试问答（项目追问）

## 1. 为什么主实验还没有进入训练？

因为预注册门禁没有通过，而不是因为不会跑训练。API 主样本在固定采样配置下 `stable=0`：
stress on run 2/10 共 20 次 rollout，只有 4 条 `intermittent` 格式违反；`deepseek-flash`
的 dev/test pilot 各 70 次、五维难度调参 110 次也都没有 `>=6/10` 的 stable 检查项。
1.5B 小基座 v7 + CTX 重跑合计 110 条有效 rollout，出现 20 个 stable 检查项，说明稳定违反
只在 1–2B 基座上出现。`final-test-v1` 因 `U-FT10/11` 的 prompt/fixture 不一致作废；
`final-test-v2` 重新冻结并完成两轮：

- S0：110 条、0 error、19 个原始 stable、剔除步数失败后 15 个 valid stable，分布在 6 个
  任务，task_success 40/110；
- S1（prompt 层输出前自检）：110 条、0 error、24 个原始 stable、20 个 valid stable，
  task_success 降到 10/110，并把 `U-FT03/10/11` 从 10/10 成功推到 0/10。

S1 是负收益，按门禁不工程化；主实验四组对比（baseline / 系统侧 / 训练 / 组合）和阶段 C
均未启动，S2 constrained decoding 仍是 0 rollout。出现 stable 只证明“有信号”，不证明
“训练有增益”。

训练侧另做了一次**独立的 1.5B QLoRA 小规模验证**，不冒充主实验训练组：train 89 /
val 30、22 个 optimizer step；held-out 6 任务 × 10 rollout，task_success 从 10/60
（16.7%）到 20/60（33.3%）。但 BASE 持平（10/30 → 10/30），HARD 提升只来自
`U-TR-B-TOOL-HARD` 的算术修正（18 → 16）；`U-TR-A-C1-HARD` 反而 10/10 重复读文件到
`max_turns`，新增 10 条步数失败。结论是“管线跑通 + 单任务行为变化 + 明显副作用”，
不是“训练普遍有效”。

7B 锚点经历了 v5 到 v9 的根因修正：v5 同一数据下 baseline `40/60`、SFT `20/60`，
BASE 从 `20/30` 掉到 `0/30`，valid stable `4 → 9`；只读诊断发现训练渲染没有向 Qwen
chat template 传 `tools=`，同一轨迹只有 307 token，而推理传入完整 schema 后为 1567
token。v9 只修模板并保留 3072 序列长度后，baseline 仍为 `40/60`，SFT 为 `60/60`，
BASE/HARD 均 `30/30`，valid stable `4 → 0`，工具结果 `160/180 → 170/170`。因此
**训练/推理模板不一致是 v5 BASE 全灭的主因**，不是“1.5B 容量瓶颈”或“训练普遍有效”。
GRPO 暂缓，原因是 Kaggle preflight 实际 0/800 rollout，过滤后池和组内方差未验证；
reward 侧已经有重复调用、额外工具和步数浪费的独立惩罚测试，不再是当前阻塞点。

## 2. 3.57% 翻转率怎么算的？

用完全相同的 11 个 dev-only 任务、`deepseek-flash`、`temperature=0.0`、`top_p=None`、
`seed=20261019` 跑两轮。每轮有 56 个检查项 × 10 次 rollout = 560 个
rollout×检查项观测；按同一 task/check/rollout 配对比较两轮的通过/失败，20 个观测翻转，
`20 / 560 = 3.57%`。它说明 `temperature=0` 和固定 seed 不能保证服务端完全确定性，
所以单轮 4/10 或 0/10 不能直接写成稳定能力。

## 3. 为什么最终选 Qwen2.5-1.5B-Instruct，而不是 Coder-1.5B、7B 或 0.5B？

7B 是原始 QLoRA 目标，但本地 MX250 不适合训练，执行环境改为 Kaggle T4 16GB；1.5B 是
在 T4/vLLM 上能跑完 110 次 Agent 实验、同时保留基本工具调用协议的最小实用基座。
0.5B 更容易“凑出”违反，但代码能力和工具协议可能先坏掉，会把能力不足误判成约束遵守问题；
所以没有为了 stable 数字继续降模型。最初选 `Qwen2.5-Coder-1.5B-Instruct`，但 v6 暴露的是
Qwen2.5-Coder 系列与 Hermes 工具调用格式不匹配：`auto` 返回 fenced JSON、`tool_calls=[]`，
`required` 才能返回真实 `read_file`；vLLM PR #47878 / #32931 也说明 Coder 需要专用
`qwen2_5_coder` parser。因此先做协议探针，确认 `Qwen2.5-1.5B-Instruct` 的 chat template
原生包含 tools 字段、`auto` 返回非空 `tool_calls`、`finish_reason=tool_calls`，再推 v7。
Coder 的失败不写成 stable=0，也不写成模型能力不足。

## 4. 小基座 v7 已经出现 stable 违反，为什么当时不直接训练？

因为 stable 违反只是路线 B 的入场券，不是训练必要性的证明。v7 + CTX 重跑合计 110 条
有效 rollout，出现 20 个 stable 检查项；但这是 dev-only ladder，不是最终 test。
`final-test-v2` 上已经先做了系统侧 S1 对照：S1 把 valid stable 从 S0 的 15 推到 20，
task_success 从 40/110 降到 10/110，属于负收益。预注册门禁要求“自检先证明收益，才评估
训练增益”；S1 未通过，所以主实验四组对比不启动。后来单独跑了 1.5B SFT 作为管线验证，
结果也没有推翻门禁：BASE 没有 task_success 增益，HARD 只修好一个算术任务，同时引入
`A-C1-HARD` 的 10/10 步数循环。否则训练组即使把格式违反压低，也无法区分是训练带来的，
还是任务/提示本来就能修好的。

## 5. 为什么 stable 阈值是 6/10？

这是实验开始前锁定的工程门禁，不是看到结果后调出来的：10 次 rollout 中 `>=6` 才算
多数稳定命中，`1–5` 记为 `intermittent`，0 次不进入 stable 统计；少于 10 次有效
rollout 记 `insufficient`。它牺牲统计精度换可执行性和可复现性。3.57% 的翻转率说明
10 次样本仍有噪声，所以报告同时保留命中数、rollout 数和翻转率，不把阈值当成显著性检验。

## 6. 为什么 pilot test 不能作为最终 test？

当前 7+7 pilot test 是在看到初版结果之后才修正检查器、补任务的，因此它不是“先预注册、
再只跑一次”的 held-out。它的 SHA-256 只能证明文件后来没变，不能证明没有结果污染。
最终 test 已升到 `final-test-v2`（11 个任务、seed `95001`–`95011`、SHA-256
`d8290751...458e`），冻结前校验 prompt 路径、行号与 FIX token，任务 ID、fixture seed、
实例与 train/dev 严格不重叠。v2 上 S0/S1 各跑 110 条一次，四组未跑；S1 是负收益，
因此不是“pilot 不能用”，而是“pilot 和 v1 都不能当最终 held-out”。

## 7. 冲突真实存在，为什么不直接归为能力问题？

`event=44` 中两组互斥约束确实同时出现在历史摘要里，模型也写对了 `unresolved_conflicts`；
但受控强冲突实验是 5/5 识别冲突、0/5 输出格式失败。失败的直接原因是 JSON 主体后追加了
自然语言，不是“冲突让模型无法输出合法 JSON”。按预注册规则，行为问题还需要 stable 命中；
该检查项在 10 次 rollout 中只命中 1 次，属于 `intermittent`。所以记录为
`sampling_noise`，不升级为“能力问题（多约束冲突）”。如果强冲突组出现稳定的格式失败，
结论会改。

## 8. constrained decoding 失败时，怎么区分基础设施失败和模型能力失败？

看失败阶段和产物：v1 是 `HFValidationError`（模型路径不存在），v2 是 `bitsandbytes`
缺失，v4 是 1.5B 权重加载 900 秒超时（日志停在 `Loading weights: 0%`），三者都发生在
生成前，rollout 数为 0，没有结果文件；所以都是基础设施失败，不能写 `json_valid` 或
“模型仍然违反”。只有模型成功加载、实际生成、输出文件和逐 run 记录都存在，才讨论
constrained decoding 的 0 违反或翻转。修复时应先打印 `/kaggle/input` 清单、用
`rglob("config.json")` 定位模型，并在找不到时明确失败；加载超时则先预加载/缓存模型。

## 9. constrained decoding 为什么 ERROR？

因为第一次 Kaggle 任务传入的模型目录
`/kaggle/input/qwen2-5-coder-7b-instruct/Qwen2.5-Coder-7B-Instruct` 实际不存在。
Transformers 在本地目录找不到 `config.json` 后把路径当成 Hugging Face repo id，抛出
`HFValidationError`。失败发生在模型/分词器加载阶段，rollout 数为 0，没有结果文件，所以
没有 `json_valid` / `snake_case_keys` 指标，不能写成模型能力失败。

已增加 `resolve_model_path()`：先检查传入目录，找不到再在 `/kaggle/input` 下用
`rglob("config.json")` 定位；仍有多个候选或找不到时明确报错并打印目录。修复已通过本地
单元测试和临时挂载目录 smoke 检查。1.5B 路径已改为 Kaggle Dataset
`xatri007/qwen2-5-1-5b-instruct` 下的 `qwen2.5-1.5b-instruct/config.json`，并用
`--preferred-model Qwen2.5-1.5B-Instruct` 指定目标；找不到时抛 `FileNotFoundError`。不会在小基座
`QUEUED` 期间重推，等 GPU 名额释放后再跑；重跑前不写任何命中率。

第二次重跑时路径已解析成功，但脚本默认 4-bit 加载，Kaggle 环境的 `bitsandbytes` 低于
`0.46.1`，在模型加载阶段报 `ImportError`，仍是 0 rollout、无指标。1.5B 在 T4 16GB 上
不需要 4-bit，因此第三次改为 fp16 加载；v3 长时间无输出后被手动取消。第四次加
`limit=5`、`max_new_tokens=256`、900 秒 wrapper 超时，路径解析成功，但权重加载停在
`Loading weights: 0%`，`TIMEOUT 900` 在 909.6 秒触发，结果 JSONL 为 0 字节。
路径错误、依赖缺失、加载超时三种状态都不能写成 constrained decoding 的命中率。

## 10. GPU 名额被占用怎么办？

先跑 `kaggle kernels list -m` 列出账号下 kernel，再对可疑 ref 逐个执行
`kaggle kernels status <ref>`，因为列表命令本身不显示状态。重点看是否存在第二个
`RUNNING` 或遗留的 `QUEUED` GPU kernel：有则取消或等它结束；如果只有目标 kernel 在
`QUEUED`，且没有其他 `RUNNING/QUEUED`，说明它在正常排队，不需要取消或重推。

截至 2026-10-20 的审计结果：协议审计 kernel 为 `COMPLETE`，小基座 v7/v8 为 `COMPLETE`，
final-test baseline v9 为 `COMPLETE`；constrained decoding v1/v2 为 `ERROR`（路径/依赖
问题），v3 已取消，v4 为 `ERROR`（加载 900 秒超时）。没有遗留的 `RUNNING/QUEUED`
kernel 需要清理。Coder-1.5B 的 v6 已确认是 Hermes 协议
不匹配，不是环境失败；`Qwen2.5-1.5B-Instruct` 协议探针通过后，v7 完成 90 条有效 rollout，
CTX 重跑完成 20 条有效 rollout。当前 Kaggle CLI
没有 `kernels delete` 子命令，也没有绕过接口做破坏性清理；旧 `COMPLETE` / `ERROR` /
404 引用不占 GPU，只保留状态记录，下次审计继续用 `status` 区分活动任务。

## 11. Coder-1.5B 为什么 `auto` 失败但 `required` 成功？

v6 在 smoke 前直接向同一 vLLM 服务发 `tool_choice=auto` 和 `required` 两次探针：
`auto` 返回 `tool_calls=[]`，模型把调用写成了 fenced JSON 文本；`required` 返回真实
`read_file({"path": "project/tuning/config_c1.ini"})`。同时 trace 的 `tools_offered`
包含 `read_file` 等六个工具，说明 schema 确实发送成功。结合 vLLM PR #47878
（Coder 不遵循 Hermes 格式）和 PR #32931（需要专用 `qwen2_5_coder` parser），根因是
系列协议不匹配，不是 chat template、parser 或工具传输故障，也不是模型能力或 `stable=0`。
改用 `Qwen2.5-1.5B-Instruct` 后，`auto` 直接返回非空 `tool_calls`，说明协议探针能区分
“模型不选工具”和“格式不被 parser 识别”。

## 12. final-test-v1 baseline 发现了什么问题？

baseline 本身跑完了：110 条 rollout、0 error、26 个 stable、9/11 个任务触发 stable，任务
成功 2/11。但复核发现 `U-FT10-BASE` / `U-FT11-HARD` 的冻结 prompt 仍引用 dev 的
`project/notes/part02.txt` / 第 37 行 / `FIX-D03`，而 `scripts/unified_eval.py` 在
`split=test` 时生成的是 `project/notes/part07.txt` / 第 53 行 / `FIX-T03`。20 次 rollout
的 40 次 `read_file` 全部返回“文件不存在”，由此造成 6 个 stable；它们不是模型行为。
剔除后仍有 20 个 valid stable、7/11 个任务触发门禁。处理方式是作废 v1、修正后冻结
`final-test-v2` 并重跑：S0 为 110 条、0 error、19 原始 stable / 15 valid stable，
task_success 40/110；S1 为 24 原始 stable / 20 valid stable，task_success 10/110。
S1 负收益，四组对比不启动；v1 只保留为“冻结前必须校验 prompt 与 fixture”的历史证据。

## 13. S1 为什么是负收益？

S1 是 prompt 层输出前自检，不是 constrained decoding。它在 `final-test-v2` 上把
task_success 从 S0 的 `40/110` 压到 `10/110`，valid stable 从 `15` 升到 `20`；还把
`U-FT03/10/11` 从 10/10 成功推到 0/10，并给 `U-FT02` 引入 10/10 步数循环。原因是自检
指令改变了输出契约、挤占了任务本身的计算/上下文预算，而不是单纯“提醒模型检查约束”。
按预注册门禁，prompt 自检不工程化。

## 14. 1.5B 有什么业务需求，为什么不是生产模型？

业务叙事是“子智能体降本”：受限工具集 + 固定输出格式的子任务，单次调用成本低、可并行。
1.5B 在这个项目里是**能力边界探针**，用来验证“训练能否补系统侧不足”，不是企业部署目标；
7B 是能力验证锚点。0.5B 没有继续尝试，因为工具协议和代码能力可能先坏掉，会把能力不足
误判成约束遵守问题。

## 15. 7B 验证了什么？

用同一份 train-v2 DeepSeek 数据、同一 6 个 held-out 任务、同一 NF4 量化路径，比较 7B
baseline 与 7B QLoRA SFT，并做了一次根因修正：

- v5：baseline `40/60`、SFT `20/60`；BASE `20/30 → 0/30`，HARD `20/30 → 20/30`，
  valid stable `4 → 9`。这是**严重退化**，不是“无增益”；
- 根因：训练渲染未传 `tools=`，同一轨迹训练 307 token、推理 1567 token；训练时模型
  根本没看到推理时的工具 schema；
- v9：只修模板并保留 3072 序列长度，baseline `40/60`、SFT `60/60`；BASE/HARD 都从
  `20/30` 到 `30/30`，valid stable `4 → 0`，两组 `within_steps=false` 都是 0，工具结果
  `160/180 → 170/170`；训练 1567 token、推理 1570 token，二者都含 tools；
- 结论：模板不一致是 v5 BASE 全灭的主因。3072 用于保留模板修复后本会被 2048 多截断的
  13 条训练样本；T4 上的非重入 checkpointing 与 Liger fused CE 只是执行层显存修复，
  不是能力变量。

边界仍是 89 train / 22 optimizer step / 6 个 held-out 任务，且 held-out 有同模板
sibling 任务，只能写“模板级泛化”，不能写“未见任务族泛化”或“训练普遍有效”。

这组 `60/60` 是 89 条 train-v2 数据上的模板验证，不要和 train-v4 380 条的
full-loss `50/60`、assistant-only `60/60` 混写。前者回答“训练/推理模板是否一致”，
后者回答“在同一数据量下 loss masking 是否改变行为”。

## 16. 为什么 AWQ 只做 baseline，不做 SFT？

AWQ 预检能加载并生成，但 `autoawq` 的 `WQLinear` 反向路径在 Kaggle 镜像上报
`ImportError: cannot import name 'PytorchGELUTanh' from 'transformers.activations'`，
AWQ + LoRA 训练不可用。为了让 baseline 与 SFT 使用完全相同的量化路径，主对比用 NF4；
AWQ 只保留 60 条 baseline 锚点（`20/60`），不与 NF4 SFT 直接相减，避免把量化差异混入
训练增益。

## 17. A-C1-HARD 的循环是训练引入还是任务诱导？

不是任务诱导。任务 prompt 只要求读一个文件并输出 JSON，fixture 只有一行，没有“每读一个
文件只回复已读”的措辞；1.5B baseline 10/10 只读一次，teacher 轨迹也只有 1–2 次调用。
1.5B SFT 后才出现 10/10 六轮重复读同一文件到 `max_turns`；7B SFT 没有复现，而是
`read_file + bash` 两轮后正常结束。v9 修复模板后，7B SFT 在 `A-C1-HARD` 上 10/10
精确读取 `project/tuning/config_c1.ini`，单轮输出合法 JSON，没有额外工具或循环。因此
当前证据指向“1.5B SFT 后的行为退化”，并保留 offline provider 固定
`tool_call_id=offline-0` 可能放大循环的 caveat；不能写成任务本身必然导致循环，也不能
把 7B 的恢复直接搬到 1.5B。

## 18. v9 同时改了 3072 和 Liger，怎么保证不是额外能力变量？

3072 不是独立能力干预，而是模板修复后的数据保留条件：模板修复后 90 条 train 中有 14 条
超过 2048 token，2048 会多丢 13 条；3072 只丢原本就超过上限的 1 条（6217 token），
所以训练仍是 89 条。Liger fused CE 与非重入 gradient checkpointing 是 T4 16GB 上避免
3072×vocab logits OOM 的执行层修复，学习率、epoch、rank、步数、数据和目标函数都不变。
严格说，v9 是“模板修复 + 3072 数据保留”的干预组，不是纯模板 token 单变量；报告里必须
这样写，不能把恢复归因于 Liger。证据见 `docs/evidence/7B_v9_唯一变量验证.md` 的
`template_probe.json` 摘要与执行条件。

## 19. 为什么从 89 条扩到 380 条？89 条能说明什么？

89 条只能验证管线：模板能否渲染、adapter 能否保存、held-out 能否跑通，不能做方法级
对照。train-v4 扩到 380 train / 80 val，覆盖 BASE/HARD/CTX/TOOL/CONFLICT 五类；
Qwen tokenizer 门禁后 19 条 train、6 条 val 超过 3072 token 被显式丢弃，实际
361 train / 74 val、90 optimizer step。xLAM 原始 60,000 行中只有 116 行能严格映射到
本地 `grep` schema，最终 92 行经本地真实执行；其余是确定性 oracle 轨迹。公开数据和
自建任务分开标注，不混口径。

89 条上的 7B v9 `60/60` 是“模板修复 + 3072 数据保留”的管线验证，不能和 380 条上的
full-loss / assistant-only / mix15 直接比较。两者回答的是不同问题：前者证明训练/推理
模板一致是前提，后者才是在同一数据量下比较 loss 和配比。

## 20. Loss masking 为什么重要？结果是什么？

Hugging Face 默认的 `DataCollatorForLanguageModeling` 会用 `input_ids` 重建 labels，
即使上游已经做了 assistant-only 掩码，也会静默退化成 full loss。项目里加了
`LabelPreservingCollator`，并加了单测；本地用同一 Qwen tokenizer 复核，361 条有效
训练行中只有 32,793 / 633,204 = 5.18% token 参与 loss。

对照是严格单变量：两次运行的 `train_manifest.config` 字典逐键相等，train 361 /
val 74、90 step、seed `20261019` 全部相同，只有 `loss_mode` 从 `full` 改成
`assistant_only`。结果：

- full-loss：`50/60`，BASE `30/30`，HARD `20/30`，CTX-HARD `0/10`；
- assistant-only：`60/60`，BASE `30/30`，HARD `30/30`，CTX-HARD `10/10`；
- 收益来自 CTX-HARD 的恢复，同时保留 A-C1-HARD 和 CONFLICT-WEAK 的修复。

边界：只有 6 个 held-out 任务、1 个 seed，assistant-only 已经触到 task_success 上限；
train_loss 不能跨条件比较（分母不同）。所以写“loss masking 在这批任务上消除了
full-loss 的 CTX 副作用”，不写“assistant-only 普遍更优”。

## 21. 数据配比为什么没救回 CTX？

预注册的假设是“纯约束数据会挤压通用能力，混 15% 通用对话可缓解灾难性遗忘”。
实际跑了 train-v4 + 67 条 Dolly（原始 447 行，门禁后 428 train / 74 val，106 step）。
结果仍是 `50/60`、BASE `30/30`、HARD `20/30`，CTX-HARD 仍 `0/10`，而且从 full-loss
的“50 次工具调用但读错/答错”变成 **0 次工具调用、`mean_steps=0`**，失败模式更重。
工具结果 `70/70` 只是“已发生调用”的成功率，不能当成覆盖率或收益。

因此这组实验只能证明：在这批 6 个 held-out 任务、15% Dolly、2 epoch 的配方下，
通用数据没有缓解 CTX 退化，反而教模型直接回答、不调工具。不能外推成“所有通用数据
配比都无效”；也没有扫 5%/30% 或其他数据源。

## 22. DPO 为什么在 T4 上 OOM？

不是版本错配，也不是 reference 用了 fp16 全权重。v3 已经固定 `private/dpo_v2/` 的
45 train / 13 val，并把 policy 初始化对齐到 train-v5 assistant-only adapter
（`f5b685d4...29fea7`）；train、val、adapter 三个 SHA 在 kernel 内全部校验通过。
reference 走同一 4-bit NF4 基座关闭 adapter，不另起一份 7B。

失败发生在 TRL 的 reference precompute：`precompute_ref_batch_size=1` 仍会把
chosen/rejected 拼成两行，实际 shape 是 `2 × 3008 × 151,643 = 912,284,288` 个 logits，
FP32 `log_softmax` 缓冲约 3.40 GiB；T4 14.56 GiB 在请求 3.21 GiB 时只剩 122.81 MiB，
因此在 `Train dataset reference log probs: 0/45` 直接 OOM。没有产生 optimizer step、
DPO adapter 或 held-out 结果。

显存预算按保守口径是 17–21 GB，24GB 卡仍有 3–7 GB 余量，所以下一步应先用 24GB 做
一次 `max_steps=1` smoke；40GB 只作 OOM 后的 fallback。但当前环境没有租卡接口/凭据，
本轮没有实际执行，不能写“24GB 不支持”。

## 23. 补数据为什么在饱和 held-out 上无增益？

补数据解决的是训练覆盖，不是自动提高 held-out 分数。train-v5 扩到 468 train / 84 val，
CTX-HARD 从 0 条有效样本补到 37 条；但原来 6 个行为 held-out 任务的 assistant-only
结果已经是 `60/60`（BASE/HARD 均 `30/30`），没有剩余空间。补数据后逐任务结果完全一样，
所以正确结论是“当前 held-out 已饱和，补数据的价值在训练集覆盖长上下文”，不能写成
“补数据带来增益”，也不能写成“补数据无效”。

如果要验证补数据或 DPO 的方法差异，需要换更难、更长或任务族不重叠的 held-out；
继续在同一批 6 个任务上重复跑，只会得到天花板数字。这也是项目收尾时保留的评测边界。

## 24. GRPO 为什么是可选分支、当前不启动？

GRPO 的阻塞不是 reward 公式本身。reward 回归实际跑的是
`tests/test_training_reward.py`（5 个）、`tests/test_reward_penalties.py`（4 个）、
`tests/test_reward_validation.py`（2 个），共 11/11 通过，已经覆盖 `tools_allowed`、
重复调用、答案后调用和 `within_steps`。用户提到的 `tests/test_reward.py` 不存在。

真正的问题是 Kaggle preflight 没有产出：v1 是 `ModuleNotFoundError: agent` 的打包/路径
错误；v2 首次状态查询返回 403，复诊为 `ERROR` 且 `failure_message` 为空，输出目录没有
`summary.json` 或 `runs.jsonl`；100 条候选 prompt × 8 次采样的实际 rollout 是 0/800。
因此 `grpo_prompts_filtered.jsonl` 没有生成，20%–80% 过滤后池数量和组内方差都未验证。
按当前指令不修打包、不修 token、不重推，GRPO 保持“可选、不启动”。

这不能写成“GRPO 无效”或“组内方差不足”：0 条 rollout 不提供方差证据。未来恢复时先修
`src` 的 import path 和 `kernels.get` 权限，最多重试一次；staging 3 条通过且拿到
≥50 条 20%–80% prompt 后，才进入 GRPO 训练分支。
