## 教师模型锁定与小样本协议验证（2026-10-21）

### 1. 当前实现里的教师是谁

`training/build_sft_dataset.py` 原先只从环境变量读取模型，manifest 没有记录教师，属于
“教师未定”状态。现已写死默认值并在 manifest 落盘：

| 项 | 值 |
| --- | --- |
| 教师模型 | `deepseek-flash` |
| 接入方式 | OpenAI-compatible `chat/completions`，base URL `https://api.deepseek.com/v1` |
| 协议版本 | `openai_chat_completions_tool_calls_v1` |
| 转换层版本 | `openai_and_hermes_to_qwen_chatml_v1` |
| 采样 | `temperature=0.0`、`top_p=None`、`seed=20261019` |

`deepseek-flash` 不是首选同系列教师。优先候选是 `Qwen2.5-7B-Instruct` /
`Qwen2.5-Coder-7B-Instruct`，因为与 `Qwen2.5-1.5B-Instruct` 共享 chat template 和工具
调用协议；但当前只有 DeepSeek API 可用，7B 教师若走本地/Kaggle 推理会与学生训练争抢
T4 名额，因此本轮采用“DeepSeek 教师 + 显式协议转换层”的备选方案，而不是假装 Qwen 7B
教师已经跑过。

- **实测触发次数为 0**：21 条可用样本（16 train + 5 val）的
  `metadata.converted_tool_calls` 全为 0，说明 deepseek-flash 通过 OpenAI-compatible
  `chat/completions` 原生返回 `assistant.tool_calls`（`type=function`、
  `function.arguments` 为 JSON 字符串），未走 Hermes fenced JSON 转换；
- 转换层因此是防御性路径，而不是唯一兼容手段：教师切换或输出漂移时仍会转换并校验；
  当前证据支持“协议兼容 + 转换层 0 次触发”，但不能写成“仅靠转换层才兼容”。

### 2. 协议转换层做了什么

- 原生 OpenAI `assistant.tool_calls`（`type=function`、`function.name`、
  `function.arguments`）原样保留；
- 如果教师把工具调用写成 fenced JSON（Hermes 风格），转换层把它转成原生
  `tool_calls`，并给下一条 `tool` 消息补上匹配的 `tool_call_id`；
- 转换后做确定性校验：没有匹配 `tool_call_id` 的 `tool` 消息、缺函数名、参数不是 JSON
  文本、`type` 不是 `function`，全部拒绝，不进入 SFT 数据；

用 `Qwen/Qwen2.5-1.5B-Instruct` 的真实 tokenizer（transformers，CPU 侧）对已生成的

```
</tool_call>
```

`run_manifest.json` 记录 `over_max_length`。SFT smoke 实际使用 15 train / 4 val。

复现：

```powershell

python -m training.check_sft_format --data private/sft_data/val.jsonl --limit 0 --out private/sft_data/format_check_val.json
```

## SFT 管线验证：1.5B QLoRA smoke（2026-10-21，非增益实验）

目的只是验证“数据 → Qwen chat template → 4-bit QLoRA → adapter 落盘”这条管线能跑通，
不报告任何训练增益。数据为当前 16 train / 5 val；超过 4096 token 的 2 条被显式过滤，
实际使用 **15 train / 4 val**，过滤清单写入 `run_manifest.json` 的 `over_max_length`。

| 项 | 结果 |
| --- | --- |
| 基座 | `Qwen/Qwen2.5-1.5B-Instruct`，4-bit NF4 |
| LoRA | r=64，alpha=128，all-linear，dropout=0.05 |
| batch / 累积 | 1 × 8，max_seq_length=4096 |
| 设备 | Tesla T4，14.56 GB |
| 可训练参数 | 73,859,072 / 962,475,520（7.67%） |
| 训练步数 | 2 个 optimizer step（15 条 ÷ 累积 8 向下取整，2 epoch 实际约 1.07 个数据 pass） |
| train_loss | 2.1728（逐 step：1.998、2.3477） |

- Kaggle CLI 下载 295 MB 的 adapter 时本地落成 0 字节，但 kernel 内 `stat` 为

## S2 staging：两次失败与止损（2026-10-21）

S2 的预注册定义是 `s1t + vLLM guided JSON decoding`。staging 只跑
`U-FT01-BASE` 3 次，通过标准是 `errors==0` 且至少 1 条 `task_success=true`。实际结果：

| kernel | 结果 | 失败阶段 | 真实原因 | rollout |
| --- | --- | --- | --- | ---: |
| v25 | `ERROR` | `difficulty_tuning.py` import | kernel 包漏了 `training/train_split.py`，`ModuleNotFoundError` | 0 |
| v26 | `ERROR` | `VLLMOfflineProvider.__init__` | vLLM 0.12 下 `GuidedDecodingParams` 不在旧路径；`ModuleNotFoundError: vllm.model_executor.guided_decoding` | 0 |

v25 不是环境限制，是打包 bug；已把 `training/train_split.py` 加入 kernel 文件清单。
v26 是真实的 vLLM 0.12 API 变动：`vllm.sampling_params` 中已没有
`GuidedDecodingParams`，旧 fallback 路径也不存在。离线 provider 现在按
`vllm.sampling_params` → `vllm.config` → `vllm.model_executor.guided_decoding` →
`vllm.entrypoints.openai.protocol` 依次探测，并在全部失败时抛
`RuntimeError("guided_decoding_unavailable: ...")`，不再裸 `ModuleNotFoundError`。

按预注册止损规则，**S2 不再推第三次**：

- S2 staging 未通过，S2 全量 110 条 **0 rollout**；
- 不把这次失败写成 `stable=0` 或模型能力结论；
- S2 代码和预注册保留，后续只有在确认 vLLM 0.12 的 guided decoding 入口后才补跑；
- 主线继续用 S0 / S1 / `s1t` / SFT，不因 S2 阻塞。

## 教师公平性复核与 train-v2 重跑（2026-10-21）

用户提出“train-v1 可能隐性偏好 DeepSeek”，因此做了一次只读公平性审计，并只在确认
两个任务定义歧义后改 prompt，未改 seed、约束、检查项或难度。审计与逐条失败见
`docs/evidence/任务定义公平性审计.md`、`docs/evidence/coder_flash_12失败归类.csv`。

**审计结论**：

- prompt 措辞、工具 schema description、fixture 路径、判分器宽容度都没有发现 DeepSeek
  专属偏好；DeepSeek 自己也有 3 条 fenced JSON/额外文字失败，说明判分器没有偏袒它。
- 发现两个与 harness 语义耦合的歧义：CTX-HARD 的“每读一个文件只回复已读”与 3 轮用户
  消息冲突；CONFLICT-STRONG 的“创建 target.txt”与 `no_arbitrary_file`（文件不得存在）
  不一致。两者都只在 train-v2 中澄清，dev/final-test-v2 未动。
- coder-flash 的 12 条 v1 失败：任务歧义 3、格式 1、能力/行为 8；格式占比只有 1/12，
  因此没有启动 coder-flash 的 JSON mode / guided decoding 44 条重跑。

**train-v2 双教师重跑**（22 任务 × 2 rollout，temperature=0.0、top_p=None、
seed=20261019）：

| 教师 | train-v1 | train-v2 | 结论 |
| --- | ---: | ---: | --- |
| DeepSeek `deepseek-flash` | 40/44 | **40/44** | 稳定 |
| Qwen3 `qwen3-coder-flash` | 32/44 | **31/44** | 修正歧义后没有提升 |

Qwen 的 v2 失败集中在算术（5 条，7+9 算成 14、7 行算成 8）和冲突行为（4 条，仍写 ALPHA、

## train-v2 DeepSeek 数据 BASE/HARD 分布（2026-10-21，扩数据前置）

完整 JSONL：

- **`B-TOOL-HARD` 是真实修正**：baseline 与 SFT 都读 `part03.txt` + `part07.txt`；
  baseline 最终回 `{"total_lines": 18}`，SFT 回 `{"total_lines": 16}`。这是本次唯一
  有任务成功对应的稳定行为变化。
- **`A-C1-HARD` 是训练后出现的循环**：SFT `rollout00` 连续 6 个 `llm_turn`，每次都是

  每次都成功且内容相同，最终 `step_replies` 为空。baseline 没有同样行为。详细复核见

- **`B-CTX-HARD` 是“扫描但不综合”**：SFT 每次按 `part01..part06 → list_dir →

  更长的读取策略，但没有学会从文件内容合成答案。
- **`B-C1-BASE` 是输出契约偏移**：SFT 最终内容为

### 5.1 A-C1-HARD 循环来源复核（2026-10-22）

任务定义：prompt 要求读取 `project/tuning/config_c1.ini`，输出严格 JSON，字段为
`path` 和 `value`；fixture 只有一行 `mode = shared-96001`；`steps_limit=3`，harness
`max_turns = steps_limit + 3 = 6`。任务只有单文件、单轮读取需求，prompt 和 fixture
都没有“每读一个文件只回复已读”之类诱导多轮读取的措辞。

| 组 | rollout | `llm_turn` | `read_file` 次数/rollout | 最大连续同参数调用 | `within_steps` | 最终输出 |
| --- | ---: | ---: | ---: | ---: | --- | --- |
| baseline | 10 | 2 | 1 | 1 | true（10/10） | fenced JSON，内容正确但 `json_valid/no_fence` 失败 |
| SFT | 10 | 6 | 6 | 6 | false（10/10） | 空；停在 `max_turns` |

教师数据侧：`U-TR-A-C1-HARD` 的 10 条 teacher rollout 全部通过确定性门禁，每条只有
1–2 次工具调用，call id 唯一（如 `call_7abcb5e8...`），没有连续重复 >=3 的轨迹。
更关键的是，该任务在 train-v2 中被划入 val（`VAL_TASK_IDS`），**不在 SFT 训练集里**；
因此循环不是对训练样本的记忆，而是 SFT 后在未见任务上的行为退化。

结论：

- baseline 10/10 只读一次就停止，没有轻微循环倾向；
- prompt、fixture 和 teacher 数据都不诱导多轮重复读取；
- 当前 harness 下，循环是 SFT 后出现的，不是 baseline 已有倾向，也不是任务设计或
  teacher 数据重复模式导致。

证据边界：离线 provider 每轮把 `tool_call_id` 固定为 `offline-0`，历史会累积同名 id；
训练数据中的 teacher call id 是唯一的。baseline 只有一次调用，不会暴露这个 OOD 问题，
因此不能完全排除“重复 call id 放大循环”。7B 用同一份数据 SFT 时，需要先确认是否复现；
若复现，再把唯一 call id 作为 harness 修复项单独验证，而不是把它写成模型能力结论。

**7B 复核（2026-10-22）**：同一 `U-TR-A-C1-HARD`、同一 train-v2 数据，7B SFT 10/10
只执行 `read_file` + `bash` 两轮，`within_steps=true`，没有重复读循环。因此循环没有在
7B 复现，不能归因于任务 prompt/fixture 本身；当前证据仍指向 1.5B SFT 后的行为退化，
并保留 offline provider 固定 call id 可能放大的 caveat。详见 `docs/evidence/7B验证锚点.md`。

### 6. 结论边界

- 22 个 optimizer step 已越过“2 step 噪声”，但仍只是 **89 条 train、6 个 held-out 任务、
  每组 60 条 rollout** 的小规模验证；只做描述性报告，不写置信区间和显著性。
- 本轮不支持“SFT 增益集中在 BASE”的模板：BASE task_success 持平，HARD 的 +10 只来自
  一个算术任务；同时出现一个新的 HARD 步数循环。正确表述是
  **“管线跑通 + 单任务行为变化 + 明显副作用”**。
- 不能据此判断 1.5B 容量是瓶颈，也不能判断教师数据是瓶颈；这两者需要 7B 锚点和
  更大的分层样本。当前证据只足以否定“这次 SFT 带来了广泛约束遵守提升”。7B v5 曾因
  训练/推理模板不一致出现严重退化；v9 修复模板后恢复，见第 9 节。因此不能把 v5 的
  退化归因为 1.5B 容量瓶颈，也不能把 v9 恢复外推为训练普遍有效。
- GRPO 暂不启动：当前阻塞不是 reward 公式，而是 Kaggle preflight 实际 0/800 rollout，
  过滤后池未生成、组内方差未验证。`behavior_reward` 已加入重复调用、答案后调用、
  `within_steps` 和 `tools_allowed` 的独立惩罚，11/11 回归测试通过；仍不能在没有
  rollout 的情况下判断 GRPO 是否有效。

### 7. GRPO 前置条件与数据侧改进（2026-10-22）

GRPO 仍不启动。启动前 reward 必须同时满足：

- 同一工具、同一参数连续调用超过 2 次扣分；
- 已经产出最终答案后继续调用工具扣分；
- `within_steps=false` 直接 0 reward，不允许用格式分抵消步数失败。

这些规则已落到 `training/reward.py` 与 `training/build_sft_dataset.py` 的确定性门禁，
并有 `tests/test_training_reward.py`、`tests/test_reward_penalties.py`、
`tests/test_reward_validation.py` 覆盖（11/11 通过）。当前 124 条 accepted teacher

数据侧改进计划：

- 正样本：保留“读到答案就停止”的轨迹；最终答案后无工具调用、连续同参调用 <=2、
  `within_steps=true` 才进入 SFT。

  `tool_call_after_answer_filtered`。
- 回归门禁：`U-TR-A-C1-HARD` 必须满足 `within_steps=true`、无连续同参调用 >2、

## 9. 7B 验证锚点（2026-10-22，v5 历史 + v9 最终复跑）

目的：用同一 train-v2 数据、同一 held-out 6 任务，判断 1.5B SFT 的问题是容量瓶颈、数据/
配方瓶颈，还是任务设计问题。7B 上没有重新生成教师数据。

### 9.1 v5：未传 tools 的退化结果（历史）

- 基座：`Qwen/Qwen2.5-7B-Instruct` + bitsandbytes NF4，transformers offline provider；
- baseline：60 条；SFT：同一 NF4 基座 + QLoRA r=64 / alpha=128 / all-linear，训练 89 条、
  22 个 optimizer step，再跑同样 60 条；
- 训练显存：v4 在 4096 序列第 3 步 OOM；v5 改 `max_seq_length=2048` +
  `paged_adamw_8bit` 后完成；
- 设备：Kaggle Tesla T4 14.56GB；训练 403.6s，adapter 645,975,704 bytes。

| v5 组 | task_success | valid stable | within_steps=false | 工具结果成功 |
| --- | ---: | ---: | ---: | ---: |
| baseline | 40/60 = 66.7% | 4 | 0 | 160/180 = 88.9% |
| SFT | 20/60 = 33.3% | 9 | 0 | 220/220 = 100% |

v5 的 BASE 从 20/30 降到 0/30，HARD 持平 20/30；SFT 在 `C1-BASE` 产生畸形
`<tool_call>`（`name=oriously_set`），在 `A-C1-HARD`/`CHECK-BASE`/`CONFLICT-WEAK`
引入不允许的额外工具调用。1.5B 的 `A-C1-HARD` 六轮重复读没有在 7B 复现。这组数字
保留为“模板不一致时会发生什么”的历史证据，不再作为最终结论。

### 9.2 v9：只修模板 + 3072 的复跑（最终）

v6 在 Kaggle 父进程导入 `agent` 失败；v7 在 3072 下 OOM，尝试分配 1.35 GiB；v8 加
非重入 gradient checkpointing 后仍 OOM；v9 启用 Liger fused linear cross entropy 后
训练完成。Liger 与非重入 checkpointing 是 T4 显存执行层修复，不改变数据、学习率、步数、
rank、epoch、序列长度或模板，不是能力变量。

最终配置与结果：

- 数据不变：train 89 / val 30，学习率 / epoch / rank / optimizer step 均与 v5 相同；
- 目标改动：训练渲染传入与推理一致的 tools schema；`max_seq_length=3072`；
- 3072 保留模板修复后 2048 会多丢的 13 条样本；90 条中仅 1 条超过 3072（6217 token），
  因此训练仍为 89 条；
- 训练时长 1520.1s；train_loss 0.6501 → 0.0988；adapter 总 661,861,305 bytes。

| v9 组 | task_success | BASE | HARD | valid stable | within_steps=false | 工具结果成功 |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| baseline | 40/60 = 66.7% | 20/30 = 66.7% | 20/30 = 66.7% | 4 | 0 | 160/180 = 88.9% |
| SFT | 60/60 = 100% | 30/30 = 100% | 30/30 = 100% | 0 | 0 | 170/170 = 100% |

训练渲染同一轨迹为 1567 token，推理为 1570 token，二者都含 `# Tools` / `<tools>`；
3 token 差异来自推理必然追加的 `<|im_start|>assistant\n`。修复前是 307 token 且不含
tools，因此模板不一致是 v5 BASE 全灭的**主因**，不是未经验证的候选。

结论：v9 支持“模板修复后恢复”。严格说，v9 验证的是“模板修复 + 3072 数据保留”这组
干预；3072 解决的是模板修复后的样本截断，不是额外能力提升。边界仍是 89 train / 22 step /
6 个 held-out 任务，且 held-out 与 train 有同模板 sibling，只能写“模板级泛化”，不能外推
成“未见任务族泛化”或“训练普遍有效”。完整证据见
`docs/evidence/7B_v9_唯一变量验证.md` 与 `docs/evidence/7b_sft_base_hard_v9.csv`。

### 10.5 Loss masking 对照：full vs assistant-only（2026-10-22）

**假设**：全序列 loss 会让模型同时学习复述 system prompt、user 文本和 tool response；
assistant-only loss 只监督模型自己生成的 tool-call JSON 与最终回答，应减少“复述观察结果”
带来的行为副作用。

**单变量控制**：

- 训练数据、train/val 行数、seed、lr、rank、epoch、序列长度、量化、优化器全部相同；
- 两次运行的 `train_manifest.config` 字典逐键相等；
- 唯一差异是 `loss_mode`：`full` → `assistant_only`；
- 两次均为 train 361 / val 74、90 optimizer step、seed `20261019`。

**运行**：

- kernel：`autumnsq/lite-agent-method-assistant`，status `COMPLETE`；
- GPU：Tesla T4 14.56 GB；kernel 总时长 7268.2 s，其中训练 5050.8 s；
- adapter：645,975,704 bytes，SHA-256 `0800e998ff46d361...`；
- assistant-only 使用 `LabelPreservingCollator`，避免 Hugging Face 默认 collator 用
  `input_ids` 重建 labels 而静默退化为 full loss；本地用同一 tokenizer 复核，
  361 条有效训练行中只有 32,793 / 633,204 = 5.18% token 参与 loss。

**held-out 结果**（同一 6 任务 × 10 rollout，120 条，0 error）：

| 条件 | task_success | BASE | HARD | 工具结果 | raw stable | valid stable |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| full-loss SFT（10.2） | 50/60 = 83.3% | 30/30 = 100% | 20/30 = 66.7% | 120/120 = 100% | 2 | 2 |
| assistant-only SFT | 60/60 = 100% | 30/30 = 100% | 30/30 = 100% | 170/170 = 100% | 0 | 0 |
| 差值 | +10 | 0 | +10 | 0 | -2 | -2 |

逐任务对比（full-loss → assistant-only）：

| 任务 | full-loss | assistant-only | 变化 |
| --- | ---: | ---: | --- |
| `U-TR-A-C1-HARD` | 10/10 | 10/10 | 0 |
| `U-TR-B-CONFLICT-WEAK` | 10/10 | 10/10 | 0 |
| `U-TR-B-CTX-HARD` | 0/10（`context_read`、`answer_exact` 稳定错误） | 10/10 | +10 |
| `U-TR-B-CHECK-BASE` | 10/10，工具 20/20 | 10/10，工具 20/20 | 0 |
| `U-TR-B-C1-BASE` | 10/10 | 10/10 | 0 |
| `U-TR-B-TOOL-HARD` | 10/10 | 10/10 | 0 |

**解释**：

- full-loss 相对 baseline 的净收益是 BASE +10、HARD 净 0，其中 CTX-HARD 从 10/10
  退化到 0/10；assistant-only 把 CTX-HARD 恢复到 10/10，同时保留 A-C1-HARD 和
  CONFLICT-WEAK 的修复，因此总体达到 60/60。
- 这支持“full-sequence loss 的副作用集中在复述 tool response / 破坏上下文读取行为”，
  但不能证明 assistant-only 对所有任务类型普遍更优：本轮只有 6 个 held-out 任务、
  1 个 seed，且 assistant-only 已经触到 task_success 上限。
- stable 从 2 降到 0，减少项是 CTX-HARD 的两个稳定错误；由于其余任务本来就没有
  stable 违反，0 不能解释为“所有约束类型都更稳定”，只能说明这 6 个任务上未观察到
  stable 违反。
- train_loss 不可跨条件比较：full-loss 的 0.6179 与 assistant-only 的 0.1758 分母不同
  （后者只对 assistant token 计 loss），不能写成“loss 更低所以更好”。

**边界**：

- 单 seed（`20261019`）、单次运行、无置信区间；task_success 已饱和，若要继续区分方法，
  需要更难或更长的 held-out 任务，而不是重复这 6 个任务。
- 6 个行为 held-out task ID 在 train-v4 `train.jsonl` 中出现 0 次；它们出现在
  `val.jsonl` 中，但训练配置为 `eval_strategy=no`、`save_strategy=no`，没有按 val
  选 checkpoint，val loss 也没有参与任何模型选择。因此行为 held-out 不构成训练泄漏，
  但“val 行与行为 held-out 任务重叠”这一口径必须在报告中保留。
- 本结果只说明 assistant-only 在这批数据/任务上的行为差异，不外推到 1.5B、其他基座或
  所有约束类型。

### 10.6 数据配比对照：纯约束 vs +15% 通用数据（2026-10-22）

**假设**：纯约束/工具数据会挤压通用能力，混入约 15% 通用对话可缓解灾难性遗忘，
尤其是 CTX 长上下文读取这类需要通用指令跟随的任务。

**单变量控制**：

- 基座、seed、lr、rank、epoch、序列长度、量化、优化器、loss mode（full）全部与 10.2
  的 full-loss 基线一致；
- 数据从 train-v4 的 380 行追加 67 条 `databricks/databricks-dolly-15k` 通用样本，
  原始 447 行；Qwen tokenizer 门禁后实际训练 428 行 / val 74 行；
- 因为样本数增加，optimizer step 从 90 变为 106（53 step/epoch × 2）；
  这不是 step 对齐实验，数据配比变化必然带来 step 变化，报告时必须同时写明。

**运行**：

- kernel：`autumnsq/lite-agent-method-mix15`，status `COMPLETE`；
- GPU：Tesla T4 14.56 GB；kernel 总时长 7198.1 s，其中训练 5418.5 s；
- adapter：645,975,704 bytes，SHA-256 `4b900fd6598307da...`；
- train_loss 0.0965（与 full-loss 的 0.6179 不可直接比较：数据量、step 数和样本分布不同）。

**held-out 结果**（同一 6 任务 × 10 rollout，120 条，0 error）：

| 条件 | task_success | BASE | HARD | 工具结果 | raw stable | valid stable |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| full-loss SFT（10.2） | 50/60 = 83.3% | 30/30 = 100% | 20/30 = 66.7% | 120/120 = 100% | 2 | 2 |
| +15% Dolly（mix15） | 50/60 = 83.3% | 30/30 = 100% | 20/30 = 66.7% | 70/70 = 100% | 3 | 3 |
| 差值 | 0 | 0 | 0 | 0 | +1 | +1 |

逐任务对比（full-loss → mix15）：

| 任务 | full-loss | mix15 | 变化 |
| --- | ---: | ---: | --- |
| `U-TR-A-C1-HARD` | 10/10 | 10/10 | 0 |
| `U-TR-B-CONFLICT-WEAK` | 10/10 | 10/10 | 0 |
| `U-TR-B-CTX-HARD` | 0/10，50 次工具调用 | 0/10，**0 次工具调用**（`mean_steps=0`） | 仍失败，失败模式更重 |
| `U-TR-B-CHECK-BASE` | 10/10，工具 20/20 | 10/10，工具 20/20 | 0 |
| `U-TR-B-C1-BASE` | 10/10 | 10/10 | 0 |
| `U-TR-B-TOOL-HARD` | 10/10 | 10/10 | 0 |

**解释**：

- 15% Dolly 没有修复 full-loss 的 CTX-HARD 退化：task_success 仍是 0/10，而且从
  “继续调用工具但读错/答错”变成“完全不调用工具、直接结束”（0 次工具调用，
  `mean_steps=0`）。这不是缓解，而是失败模式恶化。
- BASE/HARD 的 task_success 与 full-loss 完全相同（BASE 30/30、HARD 20/30），
  没有观察到“通用数据保住 BASE”的额外收益；本轮也没有出现 BASE 被冲垮的证据，
  因为 full-loss 的 BASE 已经是 30/30。
- 工具结果 70/70 = 100% 是“已发生的工具调用中成功”的比例，不是“该调用的工具都调了”。
  CTX-HARD 的 0 次调用让这个指标失去解释力；必须同时看工具调用覆盖率和 task_success。
- 这组结果不能证明“通用数据配比无效”这一普遍结论，只能证明：**在这批 6 个 held-out
  任务、15% Dolly、2 epoch 的配方下，没有缓解 CTX 退化，且引入了不调用工具的新失败模式。**

**边界**：

- 单 seed、单次运行、6 个 held-out 任务、无置信区间；task_success 没有提升，不能写
  “数据配比有效”。
- 数据配比和 optimizer step 同时变化（90 → 106），所以严格说这不是“只改配比”的
  单变量实验；但 step 变化由样本数直接导致，若要分离需要固定 step 重跑，本轮未做。
- 15% 是预注册比例，未扫描其他比例；不能外推到 5%、30% 或别的通用数据源。

### 10.7 阶段 0.0a：train-v5 补数据后 assistant-only 基线（2026-10-24）

**目的与单变量边界**：train-v4 有效集缺少 CTX-HARD（3072 门禁前 19 条全部超长），阶段 0.0a 先修 fixture，再补到 train-v5。本轮只验证“补齐长上下文数据后，assistant-only SFT 在既有 6 任务 held-out 上是否变化”；不改变 loss mode、模型、量化、seed、rank、lr、epoch 或 held-out 任务。

**CTX-HARD 口径核对**：

- 本轮 train-v5 assistant-only 的 CTX-HARD 是 **10/10 → 10/10**，不是 0/10 → 非 0。
- 历史 `0/10` 属于 **train-v4 full-loss** 条件；train-v4 assistant-only 在同一 held-out 上已经是 10/10。
- 因此不能把历史 full-loss 的 CTX-HARD 0/10 归因于“训练集没有长上下文样本”。train-v5 确实修复了长上下文数据缺口，但这 6 任务 held-out 的 assistant-only 已经饱和，无法用本轮结果证明补数据带来 CTX-HARD 增益。
- 同样，train-v5 assistant-only 的 60/60 与 train-v4 assistant-only 的 60/60 持平；它说明补数据后既有能力未退化，不说明数据扩展带来了可测提升。

**解释与边界**：

- SFT 的增益集中在 baseline 的两个稳定失败任务：`U-TR-A-C1-HARD` 从 0/10 到 10/10，`U-TR-B-CONFLICT-WEAK` 从 0/10 到 10/10；其余 4 个任务 baseline 已满分，存在明显 ceiling effect。
- 工具结果正确率从 88.89% 到 100%，但这是“已发生调用中成功”的比例；不能替代工具调用覆盖率或任务完成率。
- 单 seed、单次运行、6 个 held-out 任务、无置信区间；pass^k 已饱和，不能写“训练普遍有效”或“所有约束类型都提升”。
- 6 个行为 held-out task ID 不在 train-v5 train 中；它们出现在 val/fixture 定义中，但训练配置为 `eval_strategy=no`、`save_strategy=no`，没有按 val 选 checkpoint，val loss 未参与模型选择。
- train_loss 0.1525 与 train-v4 的 0.1758 分母、样本数和配方均不同，不能据此比较优劣。
- comparison.json 中 held-out 段的 	rain_version 字段值是 	rain-v2，含义是“6 个 held-out 任务的 spec 来源版本”，用于与历史 7B 锚点保持同一套任务定义；本轮训练数据版本以顶层 	rain_version=train-v5 和 	rain_sha256 为准。两者不是同一字段，不能据此认为本轮用了 train-v2 数据。已将该常量在 	raining/kaggle/build_method_kernel.py 中显式命名为 HELDOUT_SPEC_VERSION。
- 6 个 held-out task ID 均不在 train-v5 的 train 中；其中 5 个出现在 val 的 task 定义里，但训练配置为 val_strategy=no，val 既不参与梯度也不参与 checkpoint 选择，因此不构成训练泄漏。U-TR-B-CTX-HARD 在 train/val 中都不存在。

**逐任务判定**：

- 6 个任务的 task_success 在 v4 与 v5 之间完全一致；baseline、SFT 的 pass^k 也完全一致。
- 唯一的数值差异是 `U-TR-B-CTX-HARD` 的 SFT 工具调用次数：v4 为 100 次、v5 为 120 次；两轮均为 100% 工具结果成功、10/10 任务成功，因此不是效果差异。
- stable 违反项也在 v4/v5 之间完全一致：baseline 的 `A-C1-HARD.value_correct` 与 `CONFLICT-WEAK` 三项均稳定失败；SFT 均为 0 个 stable 违反。

**结论**：补数据后 held-out 已饱和，v4 与 v5 没有可测的逐任务增益差异。train-v5 的价值在训练集覆盖（v4 有效 CTX-HARD=0，v5=37），不能被写成“补数据带来 held-out 提升”。要验证补数据的真实收益，需要换更难或更长的 held-out；当前 6 任务不能支持该结论。

**边界**：单 seed、6 任务、SFT 已 60/60，存在明显天花板效应；上述对比只能说明“无退化且无可测额外增益”，不能说明“补数据无效”或“训练普遍有效”。
