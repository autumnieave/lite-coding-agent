# 简历措辞（训练侧方法对照版，2026-10-24）

**原则**：只写真实跑过的实验和能追溯到 `docs/evidence/` 的数字。训练侧当前是
“6 个行为 held-out 任务 × 10 rollout、2 个 seed”，不是大规模 benchmark；不报置信区间，
不写“训练普遍有效”。DPO 可写“96GB 跑通 + 相对 SFT 无额外增益”，不能写“DPO 有效”。

## 一句话版本

从零实现终端 Coding Agent，建立约束违反诊断与可复现评测；在 Qwen2.5-7B 上完成
QLoRA SFT 方法对照，定位训练/推理模板不一致与 loss masking 两个关键变量。

## 简历 bullet（可直接投递的版本）

- 从零实现终端 Coding Agent（6 个内置工具、四层上下文压缩、`constraints.json` 约束保留、
  checkpoint 与 MCP stdio 客户端），未使用 LangChain/LlamaIndex，core 与 tools 保持单向依赖。
- 建立逐轮 JSONL trace 与预注册稳定性门禁：同一检查项 10 次 rollout 命中 `>=6` 才记
  `stable`；主样本 stress on run 2/10 的 20 次 rollout 中 4 条违反全部为 `intermittent`，
  `stable=0`；相同配置两轮 560 个配对观测翻转 20 个（3.57%），量化 temperature=0 下的
  API 侧非确定性。
- 构造受控冲突实验（弱/中/强 4 组 × 5 次）：强冲突 5/5 写出非空 `unresolved_conflicts`，
  但输出格式失败 0/5；因此把冲突写成“模型能识别、但不必然导致格式失败”，不升级为能力结论。
- 构建 train-v4 训练集（380 train / 80 val，Qwen tokenizer 门禁后 361/74、90 optimizer
  step）：xLAM 60,000 行中仅 116 行能严格映射到本地 `grep` schema，最终 92 行经本地真实
  执行；其余为确定性 oracle 轨迹；train/val 与 final-test-v2 严格不重叠。
- 定位 7B SFT 的 BASE 全灭根因：训练未向 Qwen chat template 传 `tools=`，同一轨迹训练
  渲染 307 token、推理 1567 token；修复模板 + 3072 序列后，7B v9 的 BASE/HARD 从
  `20/30 → 0/30` 恢复为 `30/30`（89 条历史数据，仅作模板验证）。
- 在 train-v4 上做单变量 loss masking 对照：full-loss `50/60`（BASE `30/30`、HARD
  `20/30`、CTX-HARD `0/10`）→ assistant-only `60/60`（BASE/HARD `30/30`、CTX-HARD
  `10/10`）；配置字典逐键相同，仅 `loss_mode` 不同，assistant-only 仅 5.18% token 参与
  loss。边界是 6 任务、1 seed、task_success 已饱和，不写“普遍更优”。
- 完成数据配比负结果：train-v4 + 15% Dolly（428/74、106 step）仍 `50/60`，CTX-HARD
  仍 `0/10`，且从“50 次工具调用但答错”变成“0 次工具调用、`mean_steps=0`”；据此不把
  通用数据配比写成灾难性遗忘的解药。
- 1.5B 能力边界探针：89 条数据 QLoRA SFT 从 `10/60` 到 `20/60`，HARD `0/30 → 10/30`，
  但 `A-C1-HARD` 出现 10/10 重复读循环并新增 10 条步数失败；结论限定为“管线跑通 +
  单任务行为变化”，不外推为训练增益。
- DPO 版本对齐与 96GB 执行：`private/dpo_v2` 58 对（45 train / 13 val，全部 CTX
  `code_prefix`），train-v5 adapter SHA 校验通过；T4 在完整词表 reference logits 上
  OOM，96GB RTX PRO 6000 上 smoke 与全量跑通（5 个 optimizer step）。held-out
  baseline `40/60`、SFT `60/60`、SFT+DPO `60/60`；在已饱和任务上没有测到 DPO
  额外增益，不写“DPO 有效”。
- GRPO 边界：Kaggle 基础设施预检计划 100 prompt × 8 = 800 条 rollout，实际 **0/800**
  （v1 `ModuleNotFoundError: agent`；v2 首次 403、复诊 ERROR）。`0/800` 是 rollout 数，
  不是方差；0 条 rollout 不提供方差证据，组内方差未验证。不写“GRPO 无效”，也不写
  “组内方差不足”。候选池 v2 已改用 45 个中间态任务并冻结 SHA。
- 工程交付：`pytest -q -m "not slow" -k "not mcp"` 为 `812 passed, 1 skipped,
  37 deselected`；`ruff check .` 与 `ruff format --check .` 全绿；训练/评测代码放在独立
  `training/`，未污染 core 运行时依赖。

## 不能写的表述

- 不写“SFT 提升 HARD”：train-v4 full-loss 的 HARD 是 `20/30 → 20/30`，净 0；
  A-C1-HARD 修复与 CTX-HARD 退化相互抵消。
- 不写“assistant-only 普遍更优”：只有 6 个 held-out 任务、1 个 seed，且 `60/60` 已触顶；
  只能写“在这批任务上消除了 full-loss 的 CTX 副作用”。
- 不写“训练普遍有效”或“未见任务族泛化”：held-out 规模小，且与训练任务同模板。
- 不写 DPO 增益：96GB 的 held-out 中 SFT 已 `60/60`，SFT+DPO 也是 `60/60`；T4 OOM
  不是 DPO 无效的证据，24GB 未执行也不是“24GB 不支持”。
- 不写 constrained decoding 指标：Kaggle v1–v4 均未跑通，0 rollout。
- 不写“GRPO 组内方差为 0”或“组内方差不足”：实际是 0/800 rollout，不是 0 方差；
  0 条 rollout 不提供方差证据。只能写“基础设施预检未产出 rollout，组内方差未验证”。
- 不把 7B v9 的 `60/60` 写成 train-v4 方法对照：v9 是 89 条数据上的模板修复验证。

## 面试时主动交代的边界

- 只有 2 个 seed；task_success 完全一致，stable 2→3 波动 1 项；不报置信区间。
- 行为 held-out 是 6 个任务 × 10 rollout，task_success 已饱和；要区分方法需要更难/更长的
  held-out，而不是重复同一批任务。
- train-v4 的 `val.jsonl` 含 6 个行为 held-out task ID，但训练配置
  `eval_strategy=no`、`save_strategy=no`，没有按 val 选 checkpoint；行为 held-out 不使用
  val 记录。这个口径必须在报告里保留。
