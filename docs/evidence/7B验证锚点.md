# 7B 验证锚点

> **状态更新（2026-10-22）：** 本文的 v5 结果保留为历史证据；最终结论已被 v9 唯一变量
> 复跑替代。v9 修复训练模板并把序列长度改为 3072 后，BASE/HARD 均为 30/30，详见文末
> “v9 唯一变量复跑”和 `docs/evidence/7B_v9_唯一变量验证.md`。v5 的“严重退化”仍是真实
> 历史结果，但不是当前结论。

## 目的

同任务、同 train-v2 DeepSeek 数据，比较 7B 基座上的 baseline 与 QLoRA SFT，回答：

- 1.5B SFT 的“单任务变化 + A-C1-HARD 循环”是容量瓶颈，还是数据/任务设计问题；
- 7B 上 SFT 是否仍出现 `A-C1-HARD` 循环；
- 训练增益是否只在 BASE、还是 HARD 也能出现。

这不是“7B 整体方案”对比，也不在 7B 上重新生成教师数据。
这里的 6 个 held-out 任务是 `train-v2` 的 val 任务，与 1.5B SFT held-out 完全同一组；
不是 `final-test-v2` 的 11 个 `U-FT*` 任务。这样比较的是“同数据、同任务下的基座差异”。

## AWQ 预检（2026-10-22，Kaggle T4）

kernel：`autumnsq/lite-agent-7b-preflight`，状态 `COMPLETE`。

| 检查 | 结果 |
| --- | --- |
| `Qwen/Qwen2.5-7B-Instruct-AWQ` 下载与 vLLM 加载 | 通过 |
| 模型加载显存 | 5.1961 GiB |
| KV cache | 5.71 GiB，106,848 tokens；8192 上下文最大并发 13.04x |
| 单条 AWQ 生成 | 通过（vLLM offline，`TRITON_ATTN`） |
| AWQ + LoRA 反向 | 失败：`ImportError: cannot import name 'PytorchGELUTanh' from 'transformers.activations'` |
| vLLM + AWQ + LoRA 服务 | 未执行（反向未通过） |

失败原因是 Kaggle 镜像里的 `autoawq` 与 `transformers` 版本不兼容，不是模型能力或显存不足。
`autoawq` 的 `WQLinear` 反向路径在当前工具链不可用，因此不能把 LoRA adapter 直接训练在
AWQ 权重上。

## 量化口径决策

为了让 baseline 与 SFT 使用完全相同的量化路径，主对比采用 **NF4 对称路径**：

- baseline：`Qwen/Qwen2.5-7B-Instruct` + bitsandbytes NF4，transformers offline provider；
- SFT：同一 NF4 基座 + QLoRA r=64 / alpha=128 / all-linear；
- SFT held-out：同一 NF4 基座 + PEFT adapter，transformers offline provider；
- AWQ 只作为单独的 baseline 锚点（vLLM offline），不与 NF4 SFT 直接相减。

如果把 AWQ baseline 和 NF4 SFT 直接比较，量化差异会混入训练增益，因此不这样做。

## 主实验协议

- 任务：train-v2 val 的 6 个 held-out 任务，3 BASE + 3 HARD；
- rollout：每个任务 10 次，baseline 60 条、SFT 60 条；
- 采样：`temperature=0.0`、`top_p=None`、`seed=20261019`；
- 上下文：`max_model_len=8192`、`max_tokens=512`；
- metadata：transformers offline provider 只有 `model_version`（本地模型路径），没有
  `request_id` / `system_fingerprint`；这是 in-process 推理的限制，不伪造字段；
- 数据：`private/sft_data_v2_deepseek_expanded`，train 90 / val 34；7B 训练用
  `max_seq_length=2048`，只有 1 条 train 超长被丢弃（与 4096 时相同，无额外数据损失）；
- 指标：task_success、valid stable（剔除 `within_steps=false`）、工具调用成功率、
  `within_steps=false` 次数，按 BASE/HARD/总体分拆；
- 回归门禁：`U-TR-A-C1-HARD` 必须 `within_steps=true`、无连续同参调用 >2、最终输出非空。

## BASE 全灭根因（v5 只读诊断，2026-10-22）

本轮先不重跑，审计对象是 `private/sft_data_v2_deepseek_expanded`（train 90 / val 34）、
7B SFT 的 60 条 held-out trace、7B/1.5B 两份 `run_manifest.json`，以及训练与推理的
prompt 构造代码。诊断只读，不改采样配置，也不把配置问题写成 stable 违反。

### 数据格式审计

| 检查 | train | val |
| --- | ---: | ---: |
| 样本数 | 90 | 34 |
| assistant 工具调用消息 | 89 | 53 |
| assistant 最终答案消息 | 15 | 13 |
| 单样本最多工具调用 | 10 | 14 |
| OpenAI function style 解析失败 | 0 | 0 |
| 重复 call id / call-result 不匹配 | 0 | 0 |
| 未知工具名 | 0 | 0 |
| assistant tool_call 携带非空 content | 1 | 2 |

- `oriously` / `oriously_set` 在 train 的原始 JSON 和 tokenized 文本中均不存在，因此
  `U-TR-B-C1-BASE` 的畸形 `<tool_call>{"name": "oriously_set", ...}</tool_call>` 不是从
  训练样本逐字学来的。该 rollout 第二轮 `tool_calls=[]`，最终内容也不是 JSON。
- 新门禁会拒绝上述 1 条 train 和 2 条 val 的“工具调用消息带自然语言 content”样本；这是
  格式清洗问题，但数量太小，不能单独解释 BASE `20/30 → 0/30`。
- 旧门禁把 `U-TR-A-CTX-HARD:rollout7` 这类“assistant 已回复已读，随后新 user 继续要求读
  下一批”的合法多轮误判为答案后调用；已修正为只有同一用户轮内、最终答案后再次调用工具
  才算违规。

### 训练/推理模板不一致（主因候选）

修复前的训练路径 `training/train_sft.py::render_training_text()` 调用
`tokenizer.apply_chat_template(messages, tokenize=False, add_generation_prompt=False)`，
**没有传 `tools=`**；推理路径 `training/kaggle/local_prompt.py::build_chat_prompt()` 则传入
完整 `tools`，held-out trace 的 `tools_offered` 也记录为
`bash, edit_file, grep, list_dir, read_file, write_file` 六个工具。

用保存下来的 Qwen tokenizer 对 `train-v1:U-TR-A-C1-BASE:rollout0` 做同一条轨迹的渲染：

| 渲染方式 | token 数 | 含 `# Tools` | 含 `<tools>` |
| --- | ---: | --- | --- |
| 修复前：不传 `tools=` | 307 | 否 | 否 |
| 修复后：传默认工具 schema | 1567 | 是 | 是 |

这是明确的 train/inference 分布不一致：模型训练时看到的文本没有工具 schema，推理时却被要求
在带 schema 的协议下调用工具。该不一致可以解释训练后的协议偏移，也是当前最强的“训练配置/
数据管线”主因候选；但 7B 的退化是否由它单独造成，仍需单变量重跑确认，不能仅凭现有证据断言
“7B 更敏感”。

### token 预算复核

修复模板后，完整工具 schema 会显著增加序列长度。按 Qwen tokenizer 统计 90 条 train：

| 截断阈值 | 超长条数 | 说明 |
| --- | ---: | --- |
| 2048 | 14 | 会额外丢掉 13 条，含多条 CHECK 任务 |
| 2560 | 2 | 仍丢掉 CHECK-HARD 的一条长样本 |
| 3072 | 1 | 只丢掉 `U-TR-A-CTX-HARD:rollout7`（6217 token） |
| 3584 / 4096 | 1 | 与 3072 相同 |

因此 v5 的 `max_seq_length=2048` 在“无 tools 渲染”下没有额外损失，但在修复模板后不再安全。
本轮把 7B 配置改为 `max_seq_length=3072`，保留 89/90 条训练样本；3072 是 2048 与历史 4096
OOM 之间的折中，仍需用真实 T4 重跑验证显存，不把配置改动写成已训练成功。

### 1.5B 与 7B 配置对比

| 项 | 1.5B SFT | 7B SFT |
| --- | --- | --- |
| 训练/验证样本 | 89 / 30 | 89 / 30 |
| tokenizer / chat template | 同一份 Qwen2.5 tokenizer | 同左 |
| learning rate / epochs | `2e-4` / 2 | 同左 |
| optimizer steps | 22 | 22 |
| LoRA | r=64, alpha=128, all-linear | 同左 |
| max_seq_length | 4096 | v5=2048；本轮诊断改为 3072 |
| optimizer | 默认 | v5=`paged_adamw_8bit` |

数据和 tokenizer 不是两组的差异源；22 step 偏少，但 1.5B 在同样 22 step 下没有出现 BASE 全灭，
所以步数只能算次要不确定项，不能单独解释 7B 的严重退化。

### 根因分类

- **数据噪声：排除为主因。** 没有畸形 tool_call；`oriously_set` 不在训练集；只有 1 条 train
  带非空 tool_call content，属于清洗问题而非主要信号。
- **训练配置/数据管线：主因候选。** 训练与推理的 tools schema 不一致是直接的结构性错误；
  修复后 2048 截断是次生的配置问题；22 step/lr 尚未排除但证据较弱。
- **数据分布过敏：未证实。** 同一份数据在 1.5B 上不是 BASE 全灭，模板偏移是一个可检验的
  解释；但没有做新的教师数据或分布重采样，不能把“7B 与数据分布不匹配”当结论。

## 结论（v5 历史，按预注册三分支）

本轮落在第二种：**7B 上 SFT 出现严重退化**，因此不能把 1.5B 的问题归结为“容量瓶颈”；
当前 train-v2 数据与 SFT 配方是更主要的瓶颈。这里的 `BASE 20/30 → 0/30` 是严重退化，
不能写成“无增益”或“没有正向收益”。

- BASE 从 20/30 掉到 0/30，且 SFT 的 8 个 BASE stable 全部来自新增的工具白名单/格式退化；
  HARD 持平在 20/30。总体从 40/60 掉到 20/60。
- 工具调用成功率从 88.9% 升到 100%，但这是“调用能执行”的指标，不是“调用被允许”的指标；
  SFT 在 `A-C1-HARD`、`CHECK-BASE`、`CONFLICT-WEAK` 上都引入了不允许的额外工具调用。
- `U-TR-A-C1-HARD` 的 1.5B 六轮重复读没有在 7B SFT 复现：7B SFT 是 `read_file` + `bash`
  两轮后正常结束，`within_steps=true`。因此不能把 1.5B 循环归因于任务 prompt/fixture；
  它更像 1.5B SFT 后的行为退化，并可能被 offline provider 固定 `tool_call_id=offline-0` 放大。
- 7B baseline 仍把 `project/tuning/config_c1.ini` 改写成 `tuning/config_c1.ini`，说明任务
  prompt 的相对路径写法本身有歧义；这是任务设计问题，但不是 1.5B 循环的充分原因。修正已
  单独落到 `train-v3`（A/B `C1-HARD` 的 path 必须保留 `project/` 前缀），`train-v2` 的
  历史 SHA 和结果不重写。

因此本轮结论是 **“数据/配方瓶颈”而不是“1.5B 容量瓶颈”**：同一份数据在 7B 上不但没有
恢复 BASE，反而出现更明显的工具白名单与输出格式负迁移。不能把这组结果写成“训练普遍有效”。
诊断后应做的最小验证是：只修训练模板（以及随之决定的 3072 序列长度），baseline 不动，
单变量重跑 7B SFT + held-out；v5 当时没有把这一步伪装成已完成，v9 已完成，见下节。

结果表：`docs/evidence/7b_sft_base_hard.csv`；原始 runs/traces：
`private/kaggle_pull_7b_nf4_v5/7b_nf4/heldout/{baseline,sft}/` 与
`private/kaggle_pull_7b_nf4_v5/7b_nf4/heldout_traces/{baseline,sft}/`。

## v9 唯一变量复跑（2026-10-22，最终结论）

### 执行条件

- 数据不变：仍为 train-v2 的 89 train / 30 val；baseline 不重训，held-out 6 任务 × 10
  rollout 不变；
- 学习率 `2e-4`、2 epoch、LoRA r=64 / alpha=128 / all-linear、22 optimizer step 全部与
  v5 相同；
- 目标改动只有两处：`render_training_text()` 向 Qwen chat template 传入与推理一致的
  tools schema；`max_seq_length` 从 2048 提到 3072。3072 用于保留模板修复后本会被
  2048 多截断的 13 条样本；90 条 train 中只有 1 条超过 3072（6217 token），因此最终
  仍是 89 条；
- T4 执行层额外启用非重入 gradient checkpointing 与 Liger fused linear cross entropy，
  用于避免 3072 下的 OOM。它们不改变数据、学习率、步数、rank、epoch、序列长度或模板，
  不是能力变量；不能写成“Liger 带来增益”。

执行不是一次成功：

1. v6：Kaggle 父进程导入 `agent` 失败（`ModuleNotFoundError: agent`），修复为
   `default_tool_schemas()` 自行把 `<repo>/src` 加入 `sys.path`；
2. v7：3072 + TRL 在 optimizer state 建立后 OOM，日志为 `Tried to allocate 1.35 GiB`；
3. v8：非重入 gradient checkpointing 后仍 OOM，峰值没有下降；
4. v9：启用 Liger fused CE，避免物化 3072×vocab logits，训练完成。

### 模板一致性证据

`template_probe.json` 显示同一轨迹：

| 项 | 值 |
| --- | ---: |
| 训练渲染 token | 1567 |
| 推理渲染 token | 1570 |
| 训练渲染含 `# Tools` / `<tools>` | true / true |
| 推理渲染含 `# Tools` / `<tools>` | true / true |
| token 差异来源 | 推理追加 `<|im_start|>assistant\n`（3 token） |

修复前训练渲染只有 307 token 且不含 tools；修复后训练与推理都包含完整工具 schema，
不再是 307 vs 1567。这是把“训练/推理协议不一致”从候选升级为主因的硬证据。

| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| baseline | 40/60 = 66.7% | 20/30 = 66.7% | 20/30 = 66.7% | 4 | 0 | 160/180 = 88.9% |
| SFT v9 | 60/60 = 100% | 30/30 = 100% | 30/30 = 100% | 0 | 0 | 170/170 = 100% |

逐任务变化：

- `U-TR-A-C1-HARD`：baseline 0/10，SFT v9 10/10；路径从错误的 `tuning/config_c1.ini`
  恢复为 `project/tuning/config_c1.ini`，单轮读文件后输出合法 JSON，无额外工具；
- `U-TR-B-CONFLICT-WEAK`：baseline 0/10，SFT v9 10/10；实际写入小写

- `U-TR-B-CHECK-BASE`：两组均 10/10，但 v9 SFT 不再额外调用 `grep/list_dir`，工具

- 其余三个任务两组均 10/10，无退化。

### 结论

按预注册分支，BASE `30/30 ≥ 15/30`，因此 v5 的 BASE 全灭主因是**训练/推理模板不一致**；
3072 是模板修复后的数据保留条件，不是独立能力干预。严格表述是：
