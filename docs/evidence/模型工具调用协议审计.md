# 模型工具调用协议审计

**日期**：2026-10-20  
**审计对象**：`Qwen/Qwen2.5-Coder-1.5B-Instruct`（v6）与
`Qwen/Qwen2.5-1.5B-Instruct`（协议探针）  
**审计目的**：在推送 v7 完整 ladder 前，确认 1–2B 基座能否在 vLLM 的
`--enable-auto-tool-choice --tool-call-parser hermes` 配置下产生原生 `tool_calls`。  
**结论**：`Qwen2.5-Coder-1.5B-Instruct` 不适合作为当前工具调用协议的基座；
`Qwen/Qwen2.5-1.5B-Instruct` 探针通过，已按预设分支推送 v7。本文不把协议失败写成
`stable=0`，也不把探针通过写成 ladder 结果。

## 1. Coder-1.5B：协议不匹配，不是 stable=0

### 1.1 实际现象

v6 kernel `autumnsq/lite-agent-small-model-tuning` 最终状态为 `ERROR`，但失败点不是
GPU、vLLM 或模型加载。vLLM 0.12.0 在 Tesla T4 上正常启动，`TRITON_ATTN` 后端可用，
API server 正常监听。真正失败发生在 smoke 阶段：

| 请求 | `tool_choice` | `tool_calls` | `content` | response id |
| --- | --- | --- | --- | --- |
| 探针 A | `auto` | `[]` | fenced JSON 文本（内容是 `read_file` 调用） | `chatcmpl-a22618392c67e67a` |
| 探针 B | `required` | `read_file({"path": "project/tuning/config_c1.ini"})` | 空 | `chatcmpl-8cae2337fc179290` |

Agent smoke trace 同样显示：`tools_offered` 已包含 `bash`、`edit_file`、`grep`、
`list_dir`、`read_file`、`write_file` 六个工具，但 `llm_turn.tool_calls=[]`、
`steps=0`、`required_tools_used=false`。因此不能把 v6 记成“模型在当前任务上稳定违反
约束”；它没有进入 ladder，也没有产生 110 次 rollout 结果。

### 1.2 根因

根因是 **Qwen2.5-Coder 系列与 Hermes 工具调用格式不匹配**：

- vLLM PR #47878（`[Docs] Note that Qwen2.5-Coder models do not follow the Hermes
  tool-call format`，截至审计日仍为 open、未合并）明确说明：Coder 模型不会按 Hermes
  格式输出工具调用，调用会以普通 `content` 返回，`tool_calls` 为空。
  链接：https://github.com/vllm-project/vllm/pull/47878
- vLLM PR #32931（`[Feature] Add qwen2_5_coder tool parser for Qwen2.5-Coder models`，
  截至审计日仍为 open、未合并）说明 Coder 需要专用 `qwen2_5_coder` parser，并配合
  few-shot template；当前 `hermes` parser 不能覆盖该系列。
  链接：https://github.com/vllm-project/vllm/pull/32931

`required` 模式能返回真实 `read_file` 调用，说明工具 schema、HTTP 协议、parser 入口和
vLLM 服务本身都可用；`auto` 模式返回 fenced JSON 则说明模型没有主动走 Hermes 的
tool-call 通道。两者结合指向“系列协议不匹配”，不是“模型能力不足”，也不是
“stable 违反率为 0”。

### 1.3 对结论的约束

- Coder-1.5B 不能作为“1–2B 工具调用场景 stable 违反”的基座。
- 不把 v6 的协议失败计入 110 次 ladder，不写 `stable=0`。
- 若未来因其他原因停在路线 A，正确表述是：
  “Coder-1.5B 不适合作为工具调用基座；Qwen2.5-1.5B-Instruct 探针结果见下，
  因此当前无法用 Coder-1.5B 在 1–2B 区间验证工具调用场景的 stable 违反。”
  而不是“1–2B 模型 stable=0”。

## 2. Qwen2.5-1.5B-Instruct：协议探针通过

| 项目 | 值 |
| --- | --- |
| Kaggle kernel | `autumnsq/lite-agent-tool-protocol-audit` version 1 |
| 状态 | `COMPLETE` |
| GPU | Tesla T4, 15360 MiB（双卡可见，单卡服务） |
| vLLM | 0.12.0 |
| PyTorch backend | cu129 |
| Python | 3.13.15 |
| 模型 | `Qwen/Qwen2.5-1.5B-Instruct` |
| dtype | float16 |

| 服务参数 | `--enable-auto-tool-choice --tool-call-parser hermes`，`max_model_len=4096`，`enforce_eager=True` |
| 运行时长 | 147.7 s（含模型下载与启动） |

### 2.2 chat template

`tokenizer_config.json` 的 chat template 原生包含工具分支：

| 检查项 | 结果 |
| --- | --- |
| template 可用 | 是 |
| 长度 | 2507 字符 |
| SHA-256 | `cd8e9439f0570856fd70470bf8889ebd8b5d1107207f67a5efb46e342330527f` |
| 含 `tools` 分支 | 是 |
| 含 tool call 标签 | 是 |
| 含 tool response 标签 | 是 |
| 含 `tool_calls` 字段 | 是 |

这排除了“模板没有 tools 字段”这一层原因；该模型与 vLLM 的 Hermes parser 在模板层
是对齐的。

### 2.3 `tool_choice=auto` 探针

请求使用现有工具 schema（`read_file` 等），要求模型先读取
`project/tuning/config_c1.ini`。结果：

```json
{
  "response_id": "chatcmpl-bfe12a6535f2923c",
  "model": "Qwen/Qwen2.5-1.5B-Instruct",
  "finish_reason": "tool_calls",
  "content": "",
  "content_has_fenced_json": false,
  "tool_calls": [
    {
      "name": "read_file",
      "arguments": "{\"path\": \"project/tuning/config_c1.ini\"}"
    }
  ],
  "protocol_error": null
}
```

判定：`tool_calls` 非空、`finish_reason=tool_calls`、`content` 为空且不含 fenced JSON、
无协议错误。`required` 对照因此为 `null`（auto 已通过，无需补 required 对照）。

### 2.4 分支决策

按预先约定：

- `auto.tool_calls` 非空 → 推送 v7，按原计划跑 10 次 rollout ladder，正常统计 stable
  违反率。
- `auto.tool_calls` 为空 → 记录协议不匹配，停止换模型试错，评估 3B 或路线 A。

本次属于第一种。已推送并完成 Kernel version 7：模型 `Qwen/Qwen2.5-1.5B-Instruct`，
`ROLLOUTS=10`，状态 `COMPLETE`，运行 184.7 s。v7 记录了 110 次 rollout，其中 20 次是
`context_length` 任务的 4096-token 超限 error，90 次有效；有效部分出现 **18 个 stable
违反检查项**（全部 10/10），0 个 intermittent。稳定违反集中在 `constraint_count`
（10 项）、`tool_parameters`（3 项）和 `conflict`（5 项），`check_depth` 为 0。
随后 v8 用 25 行/文件 fixture + `max_model_len=8192` 重跑 CTX 两任务，20/20 有效、0 error，
`CTX-BASE` 10/10 成功，`CTX-HARD` 新增 2 个 stable。合并 v7 + v8 后为 **110 条有效
rollout、20 个 stable**（`constraint_count` 10、`context_length` 2、`tool_parameters` 3、
`conflict` 5），完整逐任务表见 `docs/evidence/小基座v7结果.md`。

## 3. 对阶段 A / 路线 B 的影响

1. 1–2B 区间的工具调用验证应使用 `Qwen2.5-1.5B-Instruct`，不是
   `Qwen2.5-Coder-1.5B-Instruct`。
2. Coder 的失败只能作为“模型/协议选型”证据，不能作为训练必要性的证据。
3. v7/v8 已按预注册门槛统计：同一检查项 10 次 rollout 命中 ≥6 次为 stable，1–5 次为
   intermittent，0 次不出现。20 个 stable 检查项全部为 10/10，未出现 intermittent；
   没有因结果改采样配置或阈值。
4. `context_length` 的 20 次 400 不是模型违反，已单列为 insufficient；v8 通过 fixture
   缩至 25 行/文件 + `max_model_len=8192` 修复，重跑 20/20 有效、0 error。不得把这 20 次
   写成 stable=0，也不得写成 stable 违反。
5. v7 + v8 已出现行为层 stable 违反：`U-TUNE-CTX-HARD` 只读 2/10 文件并答错、
   `U-TUNE-TOOL-HARD` 的 `total_lines` 为 18（期望 16）、`U-TUNE-CONFLICT-WEAK` 未按约束
   使用小写文件名、`U-TUNE-CONFLICT-STRONG` 未声明互斥冲突而直接写文件。最终 test 已冻结
   为 `final-test-v1` 并完成 110 条 baseline（26 个 stable）；复核发现 U-FT10/11 的
   prompt/fixture 不一致，6 个 stable 无效，四组对比暂不启动，也不在本轮自动启动 SFT。
