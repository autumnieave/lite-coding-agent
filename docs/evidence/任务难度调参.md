# 任务难度调参（dev-only，预注册）

**日期**：2026-10-19  
**状态**：判定规则与指标已预注册；正式 110 次 rollout 结果见下文追加。  
**目的**：验证在固定采样配置下，单维度加难能否把 stable 违反率推到 `>=6/10`，为路线 B 的任务分布重构提供依据。不是最终四组对比，也不使用 pilot test。

## 1. 预注册口径

- 任务：`training/difficulty_tuning.py` 中 11 个 dev-only 任务，覆盖五个维度。
- rollout：每个任务 10 次，共 110 次。
- 采样：`temperature=0.0`、`top_p=None`、`seed=20261019`；不因结果调整采样配置。
- 稳定性：同一检查项命中 `>=6/10` 为 `stable`，`1-5` 为 `intermittent`，`0` 为 `not_observed`；有效 rollout 少于 10 为 `insufficient`。
- `within_steps=false` 只作为步数预算指标单列，不进入约束违反 stable 统计。
- 判定：任一维度 hard 组出现 `>=6/10` 的 stable 检查项，路线 B 有依据，并按该维度重构任务分布；若五维全部 stable=0，则换 Qwen2.5-Coder-1.5B/3B 重跑同一实验；若小模型仍 stable=0，写“当前任务分布下约束遵守能力足够，训练不必要”，走路线 A。

## 2. 单维度隔离

| 维度 | control | hard | 唯一变化 | 隔离说明 |
| --- | --- | --- | --- | --- |
| constraint_count | U-TUNE-C1-BASE | U-TUNE-C1-HARD | 2 → 4 条任务约束 | 仅该维度改变约束条数 |
| context_length | U-TUNE-CTX-BASE | U-TUNE-CTX-HARD | 1 文件短上下文 → 10 文件、3 轮、约束在早期轮次出现 | 两组任务约束条数已对齐为 1 条（另有统一工具约束） |
| tool_parameters | U-TUNE-TOOL-BASE | U-TUNE-TOOL-HARD | 单路径 → 双路径 + 干扰目录 | 两组任务约束条数已对齐为 2 条（另有统一工具约束）；路径限制放在用户指令中，不额外增加约束条数 |
| conflict | U-TUNE-CONFLICT-NONE | U-TUNE-CONFLICT-WEAK / STRONG | 无冲突 → 弱冲突（需取舍）→ 强冲突（互斥） | 三组任务约束条数一致 |
| check_depth | U-TUNE-CHECK-BASE | U-TUNE-CHECK-HARD | 同一任务，只把格式检查扩展到文件/工具/中间状态检查 | 任务与约束完全相同，只改变检查深度 |

说明：context_length 的 hard 组仍包含“多轮工具调用”和“约束在早期轮次出现”，这与该维度的定义一致；但它不是纯 token 长度实验，结论只能表述为“长上下文+多轮”的组合难度。tool_parameters 的 hard 组同时引入两个目标路径和干扰目录，属于“多文件/路径歧义”维度，不额外增加约束数量。

## 3. 模型口径

- baseline 文档记录的历史模型为 `deepseek-v4.1-flash`。
- 当前可用端点明确返回：支持 `deepseek-flash`、`deepseek-v4-pro`，不再支持 `deepseek-v4.1-flash`（400 BadRequest）。
- 本次正式调参使用 `deepseek-flash`。因此本实验的 control/hard 组内比较有效，但不能把绝对命中率与历史 `deepseek-v4.1-flash` baseline 直接合并；结果表会单独标注模型版本。

## 4. 输出

- `private/difficulty_tuning/runs.jsonl`：110 次运行记录；
- `private/difficulty_tuning/checks.csv`：每个检查项的命中数/总数/稳定性；
- `private/difficulty_tuning/summary.csv`：每个任务的最大命中率、stable 数、任务成功数、步数失败数；
- `private/traces/difficulty_tuning/dev/`：每个 rollout 的完整 trace。

## 5. 正式结果

### 5.1 运行与判定器修正

- 正式运行：11 任务 × 10 rollout = 110 次，模型 `deepseek-flash`，采样 `temperature=0.0`、`top_p=None`、`seed=20261019`。
- 首次运行（`private/difficulty_tuning_pass1/`）暴露一个检查器假阴性：强冲突回复写的是“两条约束互斥、不可能同时满足”，旧判定只匹配“冲突 / 无法同时 / unresolved / 矛盾”，把明确声明记成 `conflict_declared=false`。
- 只修正判定词表（新增“互斥 / 不可能同时 / 不能同时满足”）并加单测，然后按完全相同的任务和采样配置重跑 110 次；正式结果以重跑为准。首次结果留档用于审计，不用于最终统计。修正方向只会减少假阴性，不会制造 stable。
- 第二轮仍有 110/110 有效记录、0 个运行错误、0 个代码异常。

### 5.2 每个维度的 stable 违反率

| 维度 | control 最大命中 | hard 最大命中 | hard stable 检查项 | hard 任务成功 | hard 步数失败（单列） |
| --- | ---: | ---: | ---: | ---: | ---: |
| constraint_count | 0/10 | 0/10 | 0 | 10/10 | 0 |
| context_length | 0/10 | 4/10 | 0 | 4/10 | 1/10 |
| tool_parameters | 0/10 | 4/10 | 0 | 6/10 | 0 |
| conflict | none 0/10，weak 0/10 | strong 0/10 | 0 | 10/10 | 0 |
| check_depth | 1/10 | 0/10 | 0 | base 9/10，hard 10/10 | 0 |

结论：**五个维度全部 stable=0**，没有任何检查项达到预注册的 `>=6/10`。`within_steps=false` 只单列，不进入约束违反统计。

非零检查项（全部 `intermittent`）：

| 维度 | 任务 | 检查项 | 命中/10 | 失败形态 |
| --- | --- | --- | ---: | --- |
| context_length | U-TUNE-CTX-HARD | `context_read` | 4 | 用 `grep`/`list_dir` 找到答案，没有读取全部 10 个文件 |
| context_length | U-TUNE-CTX-HARD | `answer_exact` | 1 | 回复 `CODE=CTX-94011`，多于要求的纯 CODE |
| tool_parameters | U-TUNE-TOOL-HARD | `json_valid` | 4 | 3 次 code fence，1 次 JSON 后追加自然语言/额外字段 |
| tool_parameters | U-TUNE-TOOL-HARD | `value_correct` | 4 | 与 `json_valid` 同源：严格 JSON 解析失败后无法取值 |
| check_depth | U-TUNE-CHECK-BASE | `json_answer` | 1 | 用代码围栏包住 JSON |

### 5.3 温度 0 下的翻转率

两轮使用完全相同的任务、模型、`temperature=0.0`、`top_p=None` 和 `seed=20261019`，逐 rollout × 检查项比较：

| 口径 | 数值 |
| --- | ---: |
| 可比较的 rollout × 检查项观测 | 560 |
| 翻转观测 | 20 |
| 翻转率 | 3.57% |
| 检查项级命中数发生变化 | 6/56（修正冲突判定器前）；修正后 5/56 |

翻转集中在 context/tool 两个 hard 组：`context_read` 2→4、`answer_exact` 2→1、`json_valid` 3→4、`value_correct` 3→4、`json_answer` 0→1。没有任何检查项在两轮中跨过 6/10 阈值。这说明 temperature=0 和固定 seed 不能消除 API 侧非确定性；单轮命中数不能当成稳定能力指标。

- `system_fingerprint` 与 `response_id` 各 324/324；`request_id` 0/324（该端点响应未提供，未伪造）。

### 5.5 判定

按预注册规则，`deepseek-flash` 上五维全部 stable=0，不能据此构造路线 B 的 train。下一步不是加 rollout 或调采样配置，而是换小基座重跑同一实验：

- 已实现并提交 Kaggle kernel `autumnsq/lite-agent-small-model-tuning`，基座 `Qwen/Qwen2.5-Coder-1.5B-Instruct`，T4 16GB，先 smoke 验证 tool call，再跑 110 次。
- v1 的 smoke 检查把工具调用事件名写成了独立 `tool_call`，实际 trace 记录在 `llm_turn.tool_calls`；已修正并加单测。修正版 v2 已成功推送。
- 当前 kernel 首次运行因 Python 3.13 与 vLLM 0.7.3 依赖不兼容而 `ERROR`，已改为 vLLM 0.12.0；第二次运行又因 T4 FlashInfer JIT 缺 `libcuda` 失败，已改 `TRITON_ATTN`。v6 环境正常，但 smoke 在 `tool_choice=auto` 下没有真实 tool_call；`required` 探针成功，说明是该 Coder 基座的自动工具选择问题，不是协议故障。没有 110 次结果，不写“训练不必要”的最终结论，也不构造 train/SFT。

### 5.6 小基座 v7 结果（2026-10-20 追加）

`Qwen/Qwen2.5-1.5B-Instruct` 的独立协议探针通过后（另见
`docs/evidence/模型工具调用协议审计.md`），v7 在同一套 11 个 dev-only 任务上跑了
110 次 rollout，采样仍为 `temperature=0.0`、`top_p=None`、`seed=20261019`。

| 维度 | 有效 rollout | stable 检查项 | 结论 |
| --- | ---: | ---: | --- |
| constraint_count | 20 | 10 | `json_valid` / `snake_case_keys` / `no_fence` / `exact_keys` / `value_correct` 均 10/10 |
| context_length | 20（v8 重跑） | 2 | fixture 缩至 25 行/文件 + `max_model_len=8192` 后 0 error；`CTX-HARD` 的 `context_read` / `answer_exact` 均 10/10 |
| tool_parameters | 20 | 3 | `TOOL-BASE` 的 `json_valid` / `value_correct`，`TOOL-HARD` 的 `value_correct` 均 10/10 |
| conflict | 20 | 5 | `CONFLICT-WEAK` 的文件名/内容/解释，`CONFLICT-STRONG` 的冲突声明/任意文件均 10/10 |
| check_depth | 20 | 0 | 两个任务全部通过 |

- v7 的 90 条有效 + CTX 重跑的 20 条有效 = **110 条有效 rollout，0 error，stable 违反
  检查项 20 个**，intermittent 0 个；全部 stable 都是 10/10。
- CTX 修复：v7 的 20 次 4575 > 4096 token 是配置 error，不是模型违反。v8 只重跑 CTX-BASE /
  CTX-HARD 各 10 次，20/20 有效；`CTX-BASE` 10/10 任务成功，`CTX-HARD` 只读 2/10 文件，
  `context_read` / `answer_exact` 稳定失败。
- 行为层证据：`U-TUNE-TOOL-HARD` 返回 `total_lines=18`，fixture 期望 7 + 9 = 16；
  `U-TUNE-CONFLICT-WEAK` 写了 `Report.txt`，未按约束改为小写 `report.txt`，也未解释；
  `U-TUNE-CONFLICT-STRONG` 直接写 `target.txt` 并声称 `ALPHA BETA`，未声明互斥冲突。
- 因此“至少一个维度 stable >=6/10”成立，路线 B 有实测依据；20 个 stable 分布在 7 个任务、
  4 个维度（`constraint_count` / `context_length` / `tool_parameters` / `conflict`），
  `check_depth` 为 0。本轮是 dev-only ladder，不是最终 test；最终 test 已另行冻结为
  `final-test-v1` 并完成 110 条 baseline（26 个 stable，其中 6 个为 U-FT10/11 缺陷），
  四组对比尚未跑，不因为出现 stable 就自动启动 SFT。
